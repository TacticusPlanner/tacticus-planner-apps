## Context

See proposal.md - Why. Current shell structure (`apps/web/src/fsd/app/layout/`):

- `nav-items.ts` defines `NavItem[]` (top-level sections) each optionally carrying `children: NavSubItem[]`, plus a `mobilePlacement: "primary" | "menu"` field.
- `app-shell.tsx` renders exactly one of `DesktopShell` (`desktop-layout.tsx`) or `MobileShell` (`mobile-layout.tsx`) based on `useIsMobile()`, and computes `pageTitle` from whichever top-level `navItems` entry matches the current path. Both shells' `<header>` currently render only that title plus theme/language/tour/account controls — no subtitle.
- The mobile header's height is a single CSS custom property, `--mobile-header-height` (`mobile-layout.css`), that other components (`scroll-to-top-button.tsx`, `character-lookup-mobile-page.tsx`) already read to size their own spacing/offsets against — there's no independent height computation to keep in sync.
- The shell already has one global keyboard shortcut precedent to follow: `packages/ui/src/components/sidebar.tsx` defines `SIDEBAR_KEYBOARD_SHORTCUT = "b"` and toggles the sidebar via a `window`-level `keydown` listener checking `(event.metaKey || event.ctrlKey) && event.key === SIDEBAR_KEYBOARD_SHORTCUT`, with `event.preventDefault()` and no focus-target guard.
- `AppSidebar` (`desktop-layout.tsx`) already owns `navigationOpen`/`setNavigationOpen`, the state controlling `DesktopNavigationDialog`, and already renders the Search button that opens it.
- `packages/ui/src/components/command.tsx` exports `CommandShortcut`, a standalone styled `<span>` (not dependent on a `Command` root) already used for rendering a shortcut hint like this.
- `AppSidebar` already owns `onCreateGoal` (a prop, ultimately from `ShellContent`'s `launchCreateGoal`) and renders the Create Goal `SidebarMenuButton` that calls it directly.
- `PlayerDataSyncButton` (`apps/web/src/fsd/app/providers/player-data-sync-button.tsx`) is self-contained: it calls its own `usePlayerDataSyncStatus()` hook internally for `syncNow`/`isSyncing` and is rendered in `AppSidebar` as `<PlayerDataSyncButton />` with no props — `AppSidebar` has no access to its sync state or handler today.
- `DesktopShell`'s `AppSidebar`/`NavMenuItem` renders every top-level item, and — when that item is the active branch and has `children` — an expanded `SidebarMenuSub` list of its children.
- `MobileShell`'s `MobileBottomNav` renders `primary`-placement items directly in the bar, and every item (via `filterNavigationItems`) in the "Menu" drawer, with `children` rendered indented beneath each drawer item via `MobileDrawerSubItem`. This structure is not changing.
- `DesktopNavigationDialog` (search) and the mobile drawer's own search field both already flatten-and-filter `navItems` including `children` via the shared `filterNavigationItems`, matching on label only today.
- Every section with `children` already has its own page-level routed tab bar as the child pages' `<Outlet/>` parent (`LookupPage`, `ProgressLayout`, `GoalsLayout`, `DailiesLayout`/`RaidsLayout`, and Guild's own tab layout via `guild-registered-view.tsx`). Each of these builds its tab row from a local `tabs` array and shadcn's `Tabs`/`TabsList`/`TabsTrigger` (or `DailiesLayout`'s shared `RouteTabs` helper, which `RaidsLayout` also reuses for its own nested Today/Plan tabs).
- Dailies has no `children` in `nav-items.ts` today; its own primary tab bar (`DailiesLayout`, six tabs: Raids, Shops, Onslaught, Salvage Run, Arena, Guild Raids) is the only listing of its child pages, sourced from the separate `dailies` i18n namespace/file (`useTranslation("dailies")`) rather than `common.json` the way every other section's tab labels are.
- A survey of each active tab's own page content found several already render their own title+description block, independent of `nav-items.ts`, that duplicates what the new header now shows once title/description swap to the active child: `goals.project.title`/`pageDescription` in `projects-page.tsx` ("Projects" / "Organize goals into focused plans and control their priority."), `goals.insights.title` in `insights-page.tsx` ("Insights", no description), `onslaught.title`/`description` in `onslaught-page.tsx`, `progress.campaigns.title`/`description`, `progress.events.title`/`description`, `progress.xpIncome.title`/`description` in Progress's other three pages, and `raids.title`/`description` in `raids-layout.tsx` ("Campaign raids" / "Spend today's energy on your active project goals in priority order."). Lookup's three tabs, the Goals board tab, Guild's Members tab, and Dailies' five placeholder tabs (shared `UnderConstruction` "coming soon" widget) have no such block.

## Goals / Non-Goals

**Goals:**

- Remove the desktop sidebar's rendering of section child items, per specs/app-navigation/spec.md. Leave the mobile menu drawer's existing nested child rendering untouched.
- Add last-visited-child navigation for the desktop sidebar's multi-child section entry points. The tracking state still lives above both `DesktopShell` and `MobileShell` (in `ShellContent`) so that a child page visited via the mobile drawer, bottom bar, or search is still recorded and honored if the user later switches to desktop mid-session — but only `DesktopShell` reads it to resolve an entry path; `MobileShell` is unaffected and keeps linking every item to its own literal `path`.
- Keep `NavItem.children` in the data model (needed by search, by the mobile drawer's existing rendering, and by the last-visited-child feature to know which sections are multi-child) while removing only its _rendering in the sidebar_.
- Add a short description to every `NavItem`/`NavSubItem` (including Dailies' six, once it gains `children` — see below), rendered in the mobile drawer, the desktop search dialog, and the page header (under the title, swapping to the active child's description when one is active), and matched by the shared search filter.
- Move every section's page-level routed tab bar (Lookup, Goals, Progress, Guild, Dailies) out of page content and into the shared app-shell header, via one new shared header-tabs component reading `NavItem.children`, replacing each page's own separate `Tabs` implementation. `Dailies > Raids`' own nested Today/Plan sub-tabs stay in page content — that's a third level, out of scope for the two-level `NavItem`/`NavSubItem` model.
- Add `children` to Dailies in `nav-items.ts` (Raids, Shops, Onslaught, Salvage Run, Arena, Guild Raids) so it participates in the header-tabs move, per-child descriptions, search, and last-visited-child the same way every other multi-child section does, rather than staying a special case.
- Swap the header title to the active child's own label too (not just the description), alongside the same active-child resolution `pageDescription` already uses — the header becomes the single title+description+tabs block for whichever page is actually active.
- Where a page already rendered its own title+description independent of `nav-items.ts` (Goals > Projects/Insights, all four Progress tabs, Dailies > Raids — see Context), delete that block from the page and reuse its real copy as the corresponding item's `descriptionKey` text, instead of inventing new copy that would duplicate it with different wording.
- Add a desktop-only Ctrl/Cmd+K shortcut that toggles the navigation search dialog, discoverable via a hint on the sidebar's Search button.
- Add two more desktop-only shortcuts, each triggering the same handler its sidebar button already calls: Ctrl/Cmd+G for Create Goal, Ctrl/Cmd+Shift+S for Sync with Tacticus (inheriting the button's own disabled-while-syncing guard). Both get a shortcut hint on their sidebar button, same treatment as search.

**Non-Goals:**

- Flattening the mobile menu drawer. Per explicit product direction, the drawer keeps listing each section's child pages nested beneath it, exactly as today — this capability's mobile-drawer requirement documents that unchanged behavior as a guarded baseline rather than changing it.
- Building a _responsive_, width-measured overflow component (e.g. `ResizeObserver`-driven "how many tabs actually fit") for the desktop header's child-picker — see the new Decision below for the simpler count-based threshold actually used instead. Mobile's tab row keeps the plain horizontal-scroll treatment unchanged (no dropdown fallback on mobile at all — see below).
- Not building a sidebar flyout (Option D) or an expandable-tree sidebar (Option C).
- Persisting last-visited-child beyond the current browser tab (e.g. syncing it across tabs, or across devices/accounts via the backend) — `sessionStorage` is deliberately tab-scoped (see Decisions).
- Not adding descriptions to the desktop sidebar or the mobile bottom navigation bar — both stay icon+label only; there's no room and no request to change their compact form.
- Not touching `Dailies > Raids`' own nested Today/Raids Plan sub-tabs, or adding header descriptions for them — that third level of tabs stays exactly where it is today, in `raids-layout.tsx`'s own page content (only its now-redundant title+description block above those sub-tabs is removed, per Goals above).
- No mobile keyboard shortcuts. There's no keyboard on a touchscreen device navigating this app; mobile keeps only its existing tap targets (drawer search field, Create Goal button, Sync button).
- Not adding further shortcuts beyond Ctrl/Cmd+K (search), Ctrl/Cmd+G (Create Goal), and Ctrl/Cmd+Shift+S (Sync) — e.g. shortcuts for individual sections or other sidebar actions. Out of scope for this request.
- Not lifting `PlayerDataSyncButton`'s sync state/handler up into `AppSidebar` to centralize all three shortcuts in one place. The Sync shortcut lives inside `PlayerDataSyncButton` itself instead (see Decisions) — a smaller change than restructuring an already self-contained, already-tested component.

## Decisions

**Where last-visited-child state lives**: a single `useState<Record<string, string>>` (section path → last child path) owned by `ShellContent` in `app-shell.tsx`, updated by one `useEffect` on `pathname` there, and exposed as a resolved per-item "entry path" (or via a small hook, e.g. `useSectionEntryPath`) consumed by `DesktopShell`'s `NavMenuItem` in place of the item's raw `path`. `MobileShell` does not consume it. One subscriber — tracking every route change regardless of which shell is mounted — still lets a child page visited on mobile be honored by the desktop sidebar if the user switches platforms mid-session, even though mobile itself has no use for the resolved entry path.

- _Alternative considered_: track it only inside `DesktopShell`. Rejected — `ShellContent` conditionally mounts only one shell at a time, so a mobile visit would never be recorded, and a `DesktopShell` remount (crossing the breakpoint and back) would lose the state; lifting it above both avoids both problems.

**Persistence**: backed by `sessionStorage`, keyed e.g. `nav.lastVisitedChild` storing the `Record<sectionPath, lastVisitedChildPath>` as JSON, read once to initialize the `useState` and written on every update. `sessionStorage` is scoped to the browser tab: a reload keeps it, a new tab or a closed tab does not — which matches "during the current session" from specs/app-navigation/spec.md more literally than an in-memory-only store would (a reload is not a new session from the user's point of view).

- _Why_: the in-memory-only version loses the tracked child on any reload, which is a common enough action (manual refresh, a deploy picking up a new build, browser restore) that it undermines the feature for exactly the users it's meant to help. `sessionStorage` costs little: one `JSON.parse`/`JSON.stringify` pair, no cross-tab or cross-session concerns, and it degrades safely (parse failure or disabled storage falls back to the in-memory default of "no last-visited entry yet," never a crash).
- _Alternative considered_: in-memory `useState` only. Rejected — reload-loses-state was flagged as a real inconsistency risk (see Risks) and `sessionStorage` removes it at negligible cost.
- _Alternative considered_: `localStorage`. Rejected — persisting across tabs/browser restarts is a stronger, unrequested guarantee than "remembers where you were this session," and `sessionStorage`'s tab-scoped, close-clears lifetime is the closer match to the word "session" in the spec.

**Which sections are "multi-child" (desktop last-visited-child)**: derived from `NavItem.children.length > 1` at the `nav-items.ts` data level — no new per-item flag. Guild (`children.length === 1`) and Dailies (`children` undefined) both naturally fall through to their existing default-route behavior without special-casing.

**Determining a section's "default child"**: reuse each section's existing index-route redirect target (e.g. `/lookup` → `/lookup/character`, already encoded in `lookup/route.tsx`'s `Navigate replace` and mirrored by `nav-items.ts` ordering the default child first). No new default-child field is introduced; the desktop sidebar resolves "no last-visited entry yet" by navigating to the section's own top-level `path` and letting that section's existing index-redirect route take over, exactly as it does today for a fresh visit — the only change is that a _subsequent_ visit in the same session with a recorded last-visited child navigates straight to that child's path instead of the section's top-level path.

**Description key naming**: follow the existing label-key convention — a sibling leaf under the same i18n parent as the item's `labelKey`, suffixed `Description` (e.g. `nav.home` → `nav.homeDescription`; `unitLookup.tabs.character` → `unitLookup.tabs.characterDescription`). Each `NavItem`/`NavSubItem` gains a `descriptionKey` field (typed the same way `labelKey` is), populated for every existing top-level and child item. This keeps descriptions co-located with their labels in each locale file instead of introducing a parallel key structure.

**Description search matching**: `filterNavigationItems` is shared by both `DesktopNavigationDialog` and the mobile drawer's search field, so extending its match predicate once (label OR description, both lower-cased) covers both surfaces without duplicating filter logic.

**Header title and description resolution**: computed once in `app-shell.tsx` via the shared `resolveActiveNavigation(navItems, pathname)` helper (mirroring how `use-section-entry-path.ts` finds the active child): find the active top-level item first, then look for a `children` entry whose `path` the current pathname matches or is nested under. Both `pageTitle` and `pageDescription` resolve the same way — the active child's own `labelKey`/`descriptionKey` when one matches, else the active top-level item's own — so the header always names and describes whichever page is actually active, not just the parent section. Both resolved values, plus the active item's `children` (for the header-tabs row), are passed to both `DesktopShell` and `MobileShell` through `shellProps`.

- _Alternative considered_: resolve the description locally inside each page/route instead of centrally in `app-shell.tsx`. Rejected — the section/child match already has to happen once, and duplicating that lookup per-page would let a page's header description drift out of sync with `nav-items.ts` instead of being derived from the same single source used everywhere else in this capability.
- _Revision note_: the title originally stayed pinned to the section name even on a child page (only the description swapped) — see the proposal's original "Header description resolution" wording. Revised after implementation review: several pages already rendered their own title+description independent of `nav-items.ts` (see Context), so leaving the header title fixed while removing those blocks would have left child pages with no title context beyond the tab row. Swapping both together, matching each page's own real title, resolves this with no extra state.
- _Second revision note (desktop only)_: product review of the shipped compact-header result found the desktop title swapping to the active child redundant once the child was already the selected tab immediately below/beside it (e.g. header reading "Character" right next to a tab row where "Character" is also the highlighted tab). Desktop's title now stays pinned to the top-level section's own label (`activeItem.labelKey`) regardless of which child is active — computed as a separate `sectionTitle` value in `app-shell.tsx`, alongside the unchanged `pageTitle` (still child-swapping, still consumed by `MobileShell` only). `pageDescription` is unaffected by this and keeps swapping to the active child's own description on both platforms — only the desktop _title_ stops swapping.

**Moving page-level tab bars into the shared header**: one new shared header-tabs component (e.g. `section-tabs.tsx`), rendered by both `DesktopShell` and `MobileShell` directly beneath the title/description, given the active top-level item's `children` and reusing the same routed-tab pattern every page's own tab bar already used (`Tabs`/`TabsList`/`TabsTrigger`, or `DailiesLayout`'s `RouteTabs` helper). Each page layout that owned a tab bar (`GoalsLayout`, `ProgressLayout`, `LookupPage`, `guild-registered-view.tsx`, `DailiesLayout`) drops its own copy and relies on the shared header one instead; each page's `<Outlet/>`-rendered content is otherwise unchanged.

- _Why now, contradicting the original proposal_: the original proposal treated "page-level tab bar stays in page content" as a deliberate non-goal, matching the source recommendation's "Level 2 lives at the top of the page, not the sidebar" without specifying exactly where "top of the page" means. Product review of the shipped result (see attached screenshot) found that satisfied the letter but not the intent — with the new header description sitting above an unchanged page-level tab bar, several pages ended up showing title+description three times (header, tab bar's page, and that page's own pre-existing title+description). Moving the tab bar into the header consolidates all three into one block.
- _Alternative considered_: keep tab bars in page content as originally scoped, and only fix the duplication by deleting the redundant per-page title+description blocks (a much smaller change). Rejected by explicit product direction in favor of full consolidation.
- Third-level tabs (`Dailies > Raids`' own Today/Plan) are excluded — the header-tabs component only ever renders a top-level item's direct `children`, never grandchildren.

**Desktop header composition: static section title + inline child row, or a breadcrumb dropdown when there are too many children (third revision)**: product review of the shipped result found the desktop header's stacked two-row layout (title+description row, then a full-width tab row beneath it) too tall and visually disconnected from the sidebar's own compact entries — the desired layout puts the section's own children inline, in the _same_ row as the title, e.g. `Lookup   Character  Machines of War  NPC`. A new component, `desktop-section-header.tsx` (`DesktopSectionHeader`), replaces `desktop-layout.tsx`'s previous `<h1>` + `SectionTabs` pairing and owns this row entirely:

- Section with no children (e.g. Home): renders the plain `<h1>` title, unchanged.
- Section with `children.length` at or below a fixed threshold (`MAX_INLINE_TABS = 6` — see below): renders the `<h1>` title followed inline by a plain `<nav>` of `react-router` `Link` elements, one per child, styled as minimal text nav items (active vs. muted-foreground, no box/pill background) rather than shadcn's `Tabs` component.
- Section with `children.length` above the threshold (today, none — see below): the plain title is replaced entirely by a `DropdownMenu` trigger reading "`{Section} › {Active child} ⌄`" (e.g. "Dailies › Raids ⌄"), opening a menu listing every child; selecting one navigates to it. This is the breadcrumb pattern from the referenced source mockup.
- `pageDescription` keeps rendering as its own row beneath this one, unchanged from the previous layout — only the title/child-picker row is restructured.
- Mobile is unaffected: `MobileHeader` keeps its own existing stacked title/description-then-tab-row layout via the unchanged `SectionTabs` component (see design.md's prior mobile-specific decisions) — this compact/breadcrumb treatment is desktop-only, per explicit product direction ("I liked the mobile version implementation").
- _Why plain `Link`s instead of the `Tabs` component (revision)_: shadcn's `Tabs`/`TabsList`/`TabsTrigger` renders each item as a boxed pill with an active background, which read as too heavy sitting directly beside a plain `<h1>`. Product direction was explicit: don't use the tabs component, stack the items like plain nav items in one row instead — matching the minimal, text-only look of the dropdown branch's own menu items. `Tabs` (and `useNavigate`-driven `onValueChange`) is no longer used in the inline branch at all; each child is a real `<Link to={child.path}>`, which is also a small accessibility/UX improvement (native anchor semantics — middle-click/open-in-new-tab work) over the previous imperative-navigate approach.
- _Why the threshold is 6, not 4 (revision)_: initially set to 4 (the exact boundary separating Progress from Dailies), which routed Dailies through the breadcrumb dropdown. Product direction was to preview Dailies with every child inline instead ("I want to see how it will look"), so the threshold was raised to 6 — today's largest section (Dailies) — so every current section renders inline. The dropdown branch and its component code are kept in place, just not reachable by any current section; a synthetic multi-child fixture in `desktop-section-header.test.tsx` (no real section has more than 6 children today) exercises it directly so the coverage isn't lost.
- _Why a fixed count threshold instead of measuring available width_: every current section's child count is known statically and only changes when `nav-items.ts` itself changes — a `ResizeObserver`-driven "does it actually fit" measurement would add real complexity (layout-effect timing, resize listeners, a flash of one layout before the other on mount) for a case that, today, has zero sections past the threshold at all.
  - _Alternative considered_: `ResizeObserver`-based real overflow detection, switching to the dropdown once the child row's measured width exceeds the space available next to the title. Rejected for this change — no current section is near the threshold, so the added implementation and testing complexity buys no real behavioral difference today; revisit if a future section's child count lands ambiguously close to the fixed threshold.
- _Why the dropdown replaces the title instead of sitting beside it_: showing both the plain section title _and_ a second "Section › Child" breadcrumb next to it would repeat the section name twice in the same row. Folding the section name into the dropdown trigger itself keeps the row to one instance of the section name, matching how the inline branch also shows the section name exactly once (in the `<h1>`).
- _Accessibility_: the dropdown trigger is a native button (Radix `DropdownMenuTrigger`, no `asChild`) with the full "Section › Child" text as its visible (and thus accessible) name, so it reads sensibly to a screen reader without extra `aria-label` plumbing; each menu item is a standard `DropdownMenuItem`, reachable and selectable via keyboard the same as any other Radix dropdown in this codebase. The inline branch's `Link`s carry `aria-current="page"` on the active one.

**Fixing a spurious vertical scrollbar on horizontal tab rows (incidental fix)**: while reviewing the above, a pre-existing bug surfaced on Dailies > Raids' own nested Today/Plan sub-tabs (`RouteTabs` in `dailies-layout.tsx`, unrelated to this change's own header work) and on mobile's `SectionTabs`: both style their `TabsList` with `overflow-x-auto` alone, and per the CSS Overflow spec, setting only one of `overflow-x`/`overflow-y` to `auto` forces the other to also compute as `auto` instead of staying `visible` — so any sub-pixel vertical overflow (e.g. the "line" tab variant's underline pseudo-element) now gets clipped-and-scrolled instead of simply drawn, producing a persistent, empty-looking vertical scrollbar. Fixed by adding `overflow-y-hidden` alongside `overflow-x-auto` on both. `desktop-section-header.tsx`'s own former `TabsList` instance is moot — it no longer uses `Tabs` at all per the revision above.

**Reusing each page's real existing title/description as its `descriptionKey` text**: for every child item whose page already rendered its own title+description before this change (Goals > Projects/Insights, Progress's four tabs, Dailies > Raids), that real copy becomes the `descriptionKey` string (and the page's own block is deleted), rather than writing new descriptive copy from scratch. The `labelKey` (short form, e.g. "Onslaught") stays the header title even where the old page-level title differed slightly in wording (e.g. "Onslaught progress") — exact-wording preservation isn't the goal, deduplication is.

- _Why_: avoids two different-but-overlapping strings describing the same page (the risk this pivot exists to fix), and reuses copy a reviewer has presumably already approved once, instead of drafting new copy that could read inconsistently with the rest of the app's voice.

**Modeling Dailies with `children` too**: Dailies gains the same `NavItem.children` array every other multi-child section has (Raids, Shops, Onslaught, Salvage Run, Arena, Guild Raids, matching `dailies-layout.tsx`'s existing tab order and its route config's index-redirect target `/dailies/raids`). This was originally scoped out (see the proposal's prior non-goal) specifically to avoid new data-model work; product direction revised this once the header-tabs move made Dailies the only remaining section with an unconsolidated tab bar.

- _Labels/descriptions live in `common.json`, duplicating `dailies.json`'s existing `tabs.*` strings_: every other section's `NavLabelKey` resolves against the default `common` i18n namespace, and every render site (`t(item.labelKey)`) calls `t()` without a namespace override. Dailies' tab labels currently live in a separate `dailies` namespace/file instead, loaded on demand via `useTranslation("dailies")` only once a Dailies page mounts. Making `nav-items.ts` reference "dailies:tabs.raids"-style namespaced keys would require the `dailies` namespace to already be loaded before the shell, sidebar, drawer, or search dialog can render Dailies' children — none of which are guaranteed to have visited a Dailies page yet - risking a flash of raw keys or added Suspense complexity. Duplicating the six short label strings (and their new description strings) into `common.json` under `dailies.tabs.*`, matching the existing `progress.tabs.*`/`goals.tabs.*` pattern, avoids that risk at the cost of two source strings per label if either is ever reworded — the same accepted trade-off already documented for every other section's `descriptionKey` (see Risks).
- _Alternative considered_: preload the `dailies` namespace globally alongside `common`. Rejected — a broader, unrequested change to the app's i18n loading strategy just to unblock one section's nav labels.
- _Side effects, accepted as consistent rather than special-cased_: Dailies now qualifies as a multi-child section (`children.length > 1`), so the desktop sidebar's last-visited-child behavior now applies to it too (previously it always navigated to `/dailies`); the mobile drawer now shows Dailies' six tabs nested beneath it (previously just a flat entry, since it's `mobilePlacement: "primary"` and had no `children`); and Dailies' six tabs become directly searchable. All three follow automatically from the existing generic `children`-driven logic — no additional code path is needed, and no other multi-child section receives special-case treatment that Dailies wouldn't now also get.

**Mobile header height for the added description line**: increase `--mobile-header-height` by enough to fit one additional truncated `text-xs`/`text-sm` line (e.g. current `4rem` base grows to roughly `5rem`, kept as a single constant next to the existing one in `mobile-layout.css`, not computed). Because every mobile consumer of header height already reads this one variable (see Context), bumping it is sufficient on its own — no consumer needs a separate code change.

**Keyboard shortcut implementation**: mirror the existing `SIDEBAR_KEYBOARD_SHORTCUT` pattern verbatim — a `window`-level `keydown` listener checking modifier + key, calling `event.preventDefault()`, then invoking the matching handler. No focus-target guard (e.g. skipping when an input is focused) is added to any of the three shortcuts below, for consistency with the sidebar's existing Cmd/Ctrl+B shortcut, which has none.

- _Alternative considered_: guard the listeners so they don't fire while a text input is focused. Rejected for consistency with the existing Cmd/Ctrl+B shortcut's behavior, and because there's no existing user complaint about that shortcut firing while typing to react to.

**Where each shortcut's listener lives**: Ctrl/Cmd+K (search) and Ctrl/Cmd+G (Create Goal) are handled by one shared listener in `AppSidebar` (`desktop-layout.tsx`), since that component already owns both `navigationOpen` and the `onCreateGoal` prop. Ctrl/Cmd+Shift+S (Sync) is handled by its own separate listener inside `PlayerDataSyncButton`, since that component already owns `syncNow`/`isSyncing` and `AppSidebar` has no access to them today.

- _Alternative considered_: lift `syncNow`/`isSyncing` out of `PlayerDataSyncButton` and up into `AppSidebar` so all three shortcuts share one listener. Rejected — bigger, riskier change to an already self-contained, already-tested component for no behavioral benefit; two listeners mounted under the same `AppSidebar` tree cost nothing extra.

**Key choices and why each is safe to intercept**:

- Ctrl/Cmd+K for search: "K" is the de facto standard key for navigation/command-palette search across widely used tools (Slack, Linear, GitHub, etc.), the least surprising choice, and not reserved by any major browser.
- Ctrl/Cmd+G for Create Goal: "G" for "Goal" is the direct mnemonic. Plain Ctrl/Cmd+G is "Find Next" in Chrome/Firefox/Edge, but only while that browser's own find bar is open — otherwise the key combination is unbound and free for the page to use, so this is safe.
- Ctrl/Cmd+Shift+S for Sync: avoids two harder conflicts — plain Ctrl/Cmd+N ("New") and Ctrl/Cmd+T/W (tab management) are hard browser-reserved and cannot be `preventDefault()`-ed in any major browser, ruling out an obvious "N" mnemonic for either action; plain Ctrl/Cmd+S carries strong "Save the page/file" muscle memory that would read as a mismatched action for "Sync." Shift+S sidesteps both: it isn't a hard-reserved combination in current Chrome/Firefox/Edge, and "S" still reads as "Sync."
- _Alternative considered_: Ctrl/Cmd+N for Create Goal ("New"). Rejected outright — Chrome, Firefox, and Edge all reserve plain Ctrl/Cmd+N for "open a new browser window" at the OS/browser-chrome level, and a web page cannot intercept or override it, so the shortcut would silently fail to do anything for a meaningful share of users.
- _Alternative considered_: plain Ctrl/Cmd+S for Sync. Rejected — while browsers allow a page to `preventDefault()` it, the existing "Save page" muscle memory makes it a confusing choice for an action that isn't actually saving anything the user typed.

**Shortcut hint display**: reuse `CommandShortcut` (`packages/ui/src/components/command.tsx`) next to each button's label (Search, Create Goal, Sync), showing the Mac glyph form ("⌘K", "⌘G", "⌘⇧S") on macOS or the Windows/Linux text form ("Ctrl+K", "Ctrl+G", "Ctrl+Shift+S") elsewhere, via one shared platform-detection helper (e.g. a `isMacPlatform()` check on `navigator.userAgent`/`navigator.platform`) rather than duplicating the check three times.

## Risks / Trade-offs

- [Desktop users who relied on the sidebar as a way to jump directly between two child pages without loading the parent section's landing page first] → Mitigated by last-visited-child navigation on desktop; mobile is unaffected since the drawer keeps every child page as a direct link, and navigation search (now matching on description too) remains a full-tree jump-to-anything path on both platforms.
- [`sessionStorage` is unavailable or throws in some environments (private/incognito modes in some browsers, storage disabled by policy)] → Wrap read/write in a try/catch and fall back to the in-memory default ("no last-visited entry yet") on failure, so the feature degrades to first-visit behavior rather than breaking navigation.
- [A last-visited child path recorded in `sessionStorage` could point at a route that no longer exists if `nav-items.ts` changes between reloads within the same tab session] → Low risk in practice (`nav-items.ts` doesn't change without a full redeploy, which typically also reloads the tab); mitigate by validating the stored path is still one of the section's current `children` before using it, falling back to the default child otherwise.
- [Single shared entry-path state above both shells adds one more piece of state to `app-shell.tsx`, which already coordinates several cross-cutting concerns (create-goal sheet, catalog/player-data providers)] → Kept intentionally small (one map, one effect) and scoped to navigation only, not merged into unrelated shell state.
- [Adding a `descriptionKey` to every nav item and populating it across 4 locales is meaningful new-copy surface area, with real risk of a missed key if a future nav item is added without one] → Mitigate with a typed `descriptionKey` field (not optional) so TypeScript catches a missing description at the `nav-items.ts` definition site, plus translation/UI tests per locale (see tasks.md).
- [Growing `--mobile-header-height` permanently costs vertical space on every mobile page, on top of the existing header/nav chrome] → Accepted as the direct cost of the requested feature; keep the added line `truncate`d and single-line so the cost is fixed and small rather than growing with description length or locale.
- [A long description in some locale could overflow a single truncated line differently than others, or read awkwardly wrapped] → Mitigate by keeping every description short by convention (roughly a phrase, not a sentence) and always rendering it `truncate`d in the header, same as the existing title.
- [Ctrl/Cmd+K, +G, and +Shift+S without a focus-target guard could steal keystrokes from some future third-party embed or an input that specifically wants to handle one of those keys] → Accepted as consistent with the existing, already-shipped Cmd/Ctrl+B sidebar shortcut's behavior; not a new class of risk introduced by this change.
- [Ctrl/Cmd+G is "Find Next" while a browser's own find bar happens to be open] → Accepted: the app's shortcut only ever fires while that browser find bar is closed (the combination is unclaimed in that state in every major browser), and a user actively using in-page find is already outside the app's own navigation flow.
- [Triggering Sync via a shortcut bypasses the button's visual disabled state as the _reason_ a second press did nothing, which could look like the shortcut silently failed] → Mitigate by keeping the shortcut routed through the exact same `syncNow`/`isSyncing` guard the button uses, so the observable behavior (no second sync starts) matches clicking a disabled button; no separate error/toast is introduced for this case.
- [Dailies' tab labels/descriptions now live in both `common.json` (`dailies.tabs.*`, read by `nav-items.ts`) and the pre-existing `dailies` namespace (`tabs.*`, still read directly by `DailiesLayout`'s own `RouteTabs` call before this change is applied) — two source strings per label that could drift if only one is edited later] → Accepted per the same trade-off already made for every other section's `descriptionKey`; once the header-tabs component replaces `DailiesLayout`'s own tab rendering, `DailiesLayout` stops reading the `dailies` namespace's `tabs.*` keys directly, narrowing this to one active source (`common.json`) plus one now-unused-but-not-deleted legacy source, which a follow-up cleanup can remove.
- [Deleting a page's own pre-existing title+description block (e.g. `raids.title`/`description`, `goals.project.title`/`pageDescription`) removes that content from the page's own translation keys' usage, but the keys themselves may still be referenced elsewhere (tests, other components) or simply become dead] → Mitigate during `/opsx:apply` by grepping each key for other usages before deleting its i18n entries, not just its render site; if a key turns out to be reused elsewhere, keep the i18n entry and only remove the redundant render site.
