## Context

See proposal.md - Why. Two independent gaps in the shared farming engine (`goal-farming` + `daily-raids` features), both traced to root cause against live game-catalog data before this change was proposed:

1. `use-daily-raids.ts` builds `battlesById` via `availableCampaignBattles(battles, eventCampaignIds, activeCampaignEventId)` (`daily-raids-calc.ts`), which only checks whether a battle's `campaignGroupId` matches the currently active event — it has no concept of "has this player reached this node." `isLocationVisible` (`location-visibility.ts`) separately treats a battle with no `attemptsLeftByBattle` entry as not-exhausted, which is correct for its own narrow purpose (don't hide a node just because sync data is silent) but combines with the eligibility gap to let an unreached Extremis node through as a live recommendation.
2. `selectFarmNodes` (`goal-farming/lib/estimate.ts`) filters candidates to the minimum `energyCost / dropRate` and returns all ties unordered. `spendDay`'s stable sort by `energyCost` alone doesn't break the tie either, so the tied candidate that happens to be inserted first (following `upgrade.farmLocations` order, itself following campaign-group processing order server-side) wins regardless of value. V1's `CampaignsService.selectBestLocations` breaks this exact tie by `expectedGold` descending; the port never carried that second sort key over, and the served dataset didn't carry `expectedGold` to sort by even if it had.

## Goals / Non-Goals

**Goals:**

- Stop the engine from ever selecting a node the player hasn't reached for an event campaign.
- Match V1's tie-break so an efficiency tie resolves toward the more valuable node.

**Non-Goals:**

- Surfacing _why_ a location was excluded (e.g. an "unlocks at node 12" hint) — out of scope for both an auto-selected location and a `farmingLocationIds`-pinned one; this change only stops the bad recommendation (including a pinned recommendation that's just as wrong), it doesn't add new UI explaining the exclusion.
- Reworking `selectFarmNodes`'s primary efficiency criterion or `spendDay`'s scheduling loop — only the tie-break changes.
- Standing (non-event) campaign eligibility — unaffected; this only adds a second condition for event-campaign battles, alongside the existing active-event check.

## Decisions

**Compute node-reached eligibility inside `availableCampaignBattles`, not as a separate filter layer.** It already receives `battles` and decides event-campaign eligibility; adding the `campaign-events-progress` lookup here keeps eligibility computation in one place rather than splitting "is this event active" and "has this player reached this node" across two call sites. Signature grows to accept a `campaignEventProgressByKey: ReadonlyMap<string, { completedBattleCount: number; completedChallengeBattlesIds: readonly string[] }>` keyed by `${campaignGroupId}:${type}`, built once in `use-daily-raids.ts` alongside the existing `eventCampaignIds` memo, from `getCampaignEventProgress()` (`packages/player-data/src/queries.ts`) — the same raw synced chunk `pages/progress` already reads; not the separate `entities/player-data-override` "campaign event progress overrides" feature, which is a manual player-entered override for a different purpose.

**Node-number comparison, not a boolean "unlocked" flag.** `campaign-events-progress` only exposes `completedBattleCount` (a count), not a per-node boolean. Comparing `battle.nodeNumber <= completedBattleCount + 1` mirrors the exact arithmetic `CampaignEventProgressRecord`'s own doc comment implies ("number of sequential, non-challenge battles completed") and matches how the standing-campaign `CampaignProgressRecord.HighestCompletedBattleIndex` is already used elsewhere in this codebase for the same kind of gate — no new comparison convention introduced.

**Challenge nodes checked by exact battle-id membership, not by number.** Per the API-side `CampaignEventProgressRecord` doc comment, challenge battles are optional and completable in any order, so `completedChallengeBattlesIds` is the only reliable signal — a numeric comparison would be wrong for them. `Battle.challenge` (already on the client's `Battle` type) selects which check applies.

**`expectedGold` tie-break lives in `selectFarmNodes`, keyed by carrying the value through `FarmNode`.** `FarmLocation.expectedGold` (new, served field) is read when building `FarmNode` candidates in `selectFarmNodes`; the minimum-efficiency filter is unchanged, and a second `Array.prototype.sort` (or `reduce` to the single max, since only the selected node(s) matter downstream) picks the highest `expectedGold` among the surviving ties before returning. A location with `expectedGold: null` sorts last, per the added spec scenario.

**`farmLocationSchema`'s `expectedGold` is `.nullable().optional()`, not just `.nullable()`.** `null` and "key absent" are different, both-valid states here, not interchangeable: `null` means the served location's battle genuinely has no guaranteed gold reward (a real, expected value from the companion API's denormalizer); "key absent" means this client is talking to a catalog response that predates the field — an older cached dataset, or a deploy-ordering gap between the two independently-deployed repos despite the stated API-first convention. `farmLocationSchema` is built with `z.looseObject`, but looseness only affects _unknown_ keys; a key the schema declares is still required unless marked `.optional()`, so a plain `.nullable()` field would hard-fail `safeParse` on the "key absent" case and break the entire catalog fetch, not just omit the tie-break. The client-side `FarmLocation.expectedGold` type itself stays `number | null` (no `undefined`) — the "key absent" parse result is normalized to `null` at the same mapping boundary that constructs `FarmLocation` from the parsed payload (task 1.2), so `selectFarmNodes` only ever has to reason about two states, matching the spec's "no `expectedGold`" scenario.

**A goal's `farmingLocationIds`-pinned location is subject to the same node-reached eligibility check as an auto-selected one — no bypass.** `availableCampaignBattles` runs upstream of `selectFarmNodes`'s `farmingLocationIds`-restricted branch, so an event-campaign node a player pinned before reaching it is dropped from `battlesById` the same way an auto-recommended one would be; `selectFarmNodes`'s restricted-path lookup (`battlesById.get(location.battleId)`) then finds nothing for it and yields zero candidates for that resource. This is deliberate, not an oversight carried over from the original proposal: a pinned location that the player genuinely cannot raid is exactly as wrong a recommendation as an auto-selected one would be, so silently keeping it eligible would reintroduce this same change's own bug for the one case where the player made the choice explicitly. The resulting "zero candidates for this resource" state is not new engine behavior — it already exists today for any resource whose farm locations are all ineligible for unrelated reasons (e.g. every candidate belongs to an inactive campaign event), so no new empty-state UI is introduced; see task 2.5 for the regression test making this explicit and the added spec scenario below.

**Alternative considered — do the tie-break in `spendDay` instead of `selectFarmNodes`.** Rejected: `spendDay` operates on the flattened `spendable` list across every resource's nodes for the day, not per-resource, so it can't tell which nodes belong to the same original tie without extra plumbing. `selectFarmNodes` already computes and owns that tie set per resource, so resolving it there keeps `spendDay` unchanged.

## Risks / Trade-offs

[The `campaign-events-progress` chunk might not be populated for a campaign group the player has literally never opened] → Already handled by the spec's "no entry" scenario: treated as not-reached, i.e. excluded — the conservative direction (never recommends an inaccessible node), matching this change's purpose.

[Sequential node-number assumption could be wrong for some event campaign] → Verified against the raw catalog data for all six event campaigns (`eventCampaign1`-`eventCampaign6`: Adeptus Mechanicus, Tyranids, T'au Empire, Death Guard, Adepta Sororitas, Dark Angels), both Standard and Extremis tracks: every track has exactly 30 non-challenge nodes numbered contiguously 1-30 and exactly 3 challenge nodes, always at node numbers 3, 13, and 25, each sharing its preceding non-challenge node's number rather than carrying its own. The pattern is identical across all twelve tracks, so the comparison in "Node-number comparison" and "Challenge nodes checked by exact battle-id membership" above is not a single-campaign spot-check. Residual risk is limited to a future event campaign introduced after this change ships with a different layout — task 2.3's parameterized test across all six existing campaigns would not catch a not-yet-existing seventh one; if that happens, the fix is a data-shape correction to the comparison, not a change to the spec's intent.

[Depends on companion API change shipping `expectedGold` first] → Per this repo's cross-repo convention, the API half applies first; until it does, this repo's `datasetPayloadSchemas` update would reject the field if it arrived before the type update, so task ordering here starts with the schema/type update, deployed only after the API half is live.

## Migration Plan

No data migration. Ships as a normal frontend deploy once the companion API change's `expectedGold` field is live; the tie-break requirement is inert (no ties observed) until then only in the sense that `expectedGold` reads as `undefined`/absent from older cached catalog data, which the "no guaranteed gold" (null) handling already covers safely.
