## Context

See `proposal.md` for motivation. The Rank/Ability/Ascension "Potential progress" pipeline already exists end to end: `computePlanInsights` (`plan-insights-calc.ts`) builds a per-goal-kind allocation of a shared inventory pool in priority order (`allocatePlanInventory` for upgrade materials, `allocateOrbInventory` for alliance orbs), then `computePotentialProgressRatio` (`potential-progress.ts`) turns a goal's allocation into a 0-1 ratio on the goal's own progress scale. `goal-progress-visuals.tsx`'s `GoalProgressDisplay` already renders whatever `potentialRatio` it's given generically (striped fill, "↗ N%", info popover) — it is not gated by goal kind. The account's XP-book resource-cost math (`level-xp-cost.ts`: `xpNeededForLevelRange`, `netXpAgainstOwnedBooks`, `ownedBooksByRarity`) already exists too, built for the goal-creation form's cost preview (`use-level-goal-cost.ts`), but nothing upstream of it handles allocating one shared book pool across _several_ Level goals in priority order the way `allocatePlanInventory`/`allocateOrbInventory` already do for materials/orbs.

## Goals / Non-Goals

**Goals:**

- Give a Level goal a Potential Progress ratio, sourced from the account's owned XP books, shared by priority across a project's Level goals.
- Surface the XP still needed in the Remaining column and the explanation popover, matching the existing Rank goal's slots/energy pattern.

**Non-Goals:**

- Not changing any existing Rank/Ability/Ascension calculation or their own allocation pipelines.
- Not changing the goal-creation form's own XP-book cost preview (`use-level-goal-cost.ts`) — it already nets a single goal's need against the full owned pool in isolation, which remains correct for a form previewing one goal's own cost before it's saved.
- Not touching the flat, cross-project Goals list — Potential progress (any goal kind) only exists within a project's Insights pipeline, unchanged by this proposal.

## Decisions

1. **Model the XP-book allocation as its own small module (`level-potential-allocation.ts`), mirroring `orb-potential-allocation.ts`'s shape, rather than folding Level into `computePotentialProgressRatio`'s existing stage-based algorithm.**
   `computePotentialProgressRatio` walks a goal's `GoalInventoryAllocation`'s `stages` (rank-crossing material batches) — a structure specific to Rank/Ability's slot-based progress. A Level goal has no stages; it's one continuous XP pool with no natural "batch" boundaries. Reusing the stage machinery would mean inventing fake single-stage structures for no benefit. A dedicated `allocateXpBooksAcrossGoals(goals, ownedXpBooks): Map<goalId, potentialLevel>` — walking goals in priority order, spending from one shared, mutated book pool per goal, exactly like `allocateOrbInventory` already does for Ascension's alliance orbs — is the more direct fit, and the caller (`computePlanInsights`) converts the resulting level into a ratio inline (a 3-line `Math.min/max` calculation), not worth its own shared abstraction.

2. **Build the allocation on two new primitives in `level-xp-cost.ts`: `consumeOwnedBooks` (a pool-mutating variant of the existing `netXpAgainstOwnedBooks`) and `maxLevelReachableWithXp` (the inverse of `xpNeededForLevelRange`).**
   `netXpAgainstOwnedBooks` already implements the correct greedy, highest-value-first, whole-book-only spending algorithm (ported from V1) — but only returns the leftover XP need, not the _updated_ pool, so a caller allocating the same pool across several goals in sequence has no way to see what a higher-priority goal already spent. `consumeOwnedBooks` returns both; `netXpAgainstOwnedBooks` becomes a one-line wrapper around it (`.remainingXp`), so its existing callers and tests are unaffected. `maxLevelReachableWithXp` scans candidate levels one at a time (there are at most ~65) calling the existing `xpNeededForLevelRange`, since the level-XP curve (`xpTotalAtLevel`) has no closed-form inverse — this mirrors the same "scan candidates, stop at the first miss" pattern already used for the Rank goal's reachable-ceiling marker (`reachableRankProgress` in `rank-additional-target.ts`).

3. **The Remaining column's XP figure is the raw xp need, never netted against owned books — matching the Rank goal's own Remaining column, which shows the raw slot count, not a potential-adjusted one.**
   Keeps "Remaining" and "Potential" as two clearly separate concerns (what's still needed vs. what owned resources could cover), consistent with the existing Rank goal precedent, and avoids needing the priority-allocation pipeline (project context, other goals' priorities) just to render a Remaining-column figure that should also be visible on the flat cross-project list, which has no such context.

4. **The explanation popover's Actual/Potential clauses reuse the same figures already computed for the Remaining column and the Potential ratio's own XP allocation — no new data threaded through.**
   The Actual line's "N levels remaining" reuses `progress.target - progress.current` (already used for the Remaining column). The Potential line's "N XP remaining" reuses `progress.remainingXp` (the same raw figure) — this exactly mirrors the existing Rank goal precedent, where the Potential line's "energy remaining" clause is the farming-energy estimate for the _raw_ remaining materials, not a value re-derived from the allocation itself. Keeping the same asymmetry means no new prop needs to flow through `GoalProgressDisplay`.

5. **(Post-implementation fix) `xpNeededForLevelRange` treats `currentXp` as the character's total XP gained since level 1, not a per-level-reset partial amount — fixing a pre-existing bug this change's live verification against the real synced account exposed.**
   The function's original formula (`targetLevelTotalXp - currentLevelTotalXp - currentXp`) assumed `currentXp` reset to 0 at every level-up — but the real Tacticus API's own `xp` field is documented (`tacticus-planner-api`'s OpenAPI spec, `Unit.xp`) as "total XP gained for character": a lifetime cumulative total, never reset. Subtracting `currentLevelTotalXp` on top of a `currentXp` that already includes everything up to and past that threshold double-counted it, producing a wildly understated (sometimes negative, clamped to 0) result. This was live-verifiable: two real Level goals for different characters, both spanning the same 6-level range, independently landed on the exact same "5 of 6 levels" (83%) Potential ratio — an implausible coincidence for two different characters' XP totals unless the underlying math was structurally wrong — and two other real Level goals showed no XP figure in the Remaining column at all (the double-subtraction went negative, clamping their nonzero real need to 0). The fix drops the `currentLevelTotalXp` term entirely: `xpNeeded = targetLevelTotalXp - currentXp`. Cross-checked against V1's own production app (`tacticusplanner.app/plan/goals`) for the same account: V1's own "Total Resources Missing" aggregate reported ~3.4M XP still needed across the whole plan (expressed as ~54 Mythic-book-equivalents, 62,500 XP each) — consistent with individual high-level Level goals each needing hundreds of thousands to low millions of XP, the same order of magnitude the fix produces, and wildly inconsistent with the pre-fix ~100-200K-per-goal figures. This was a pre-existing bug in `level-xp-cost.ts` (built earlier for the goal-creation form's cost preview), not something this change introduced — this change's own live verification against real data was simply the first place it became clearly, visibly wrong.

6. **(Post-implementation fix #2) `xpBookIdRarity`'s id map used guessed `bookXxx` keys; the real synced ids are `xpXxx` — fixing a second pre-existing bug that independently zeroed every Level goal's Potential ratio regardless of fix #5.**
   The user reported every Level goal still showed exactly 0% Potential after fix #5 shipped, while V1's own production app (same account) showed several non-zero Level-adjacent progress bars — directly contradicting this change's original live-verification note (below, now superseded) that "every Level goal shows 0% Potential... an accurate reflection" of insufficient owned books. Direct read-only inspection of the app's own IndexedDB (`tacticus-planner-player-data`, `profile` store, `inventory:summary` record) showed the account's real owned counts were substantial (1919 Common / 1479 Uncommon / 633 Rare / 271 Epic / 93 Legendary / 25 Mythic — ~3.9M XP worth), but under ids `xpCommon`/`xpUncommon`/`xpRare`/`xpEpic`/`xpLegendary`/`xpMythic`, not the `bookCommon`/etc. ids `xpBookIdRarity` guessed at (risk noted below, now resolved). Since `ownedBooksByRarity` silently skips any unrecognized id rather than erroring, the mismatch zeroed the entire pool for every allocation without any visible failure. Fixed by correcting the map to the real, IndexedDB-confirmed ids.
   **Post-fix live re-verification** (project detail page, real account, `MY Goals` project, 2026-09-19): higher-priority Level goals now show real non-zero Potential (Neurothrope 100%, Ahriman 100%, Abraxas 83%), confirming the pool is no longer silently empty. Lower-priority Level goals (e.g. Arjac Lv33→35, Ragnar Lv55→60) still correctly show 0% Potential — not a bug, but the account's ~3.9M-XP pool being fully claimed by higher-priority goals first under the priority-ordered shared-pool allocation (Decision 1/2), the same shared-pool depletion behavior the existing Rank/Ascension pipelines already exhibit.

## Risks / Trade-offs

- **A Level goal's Potential ratio depends on every _other_ Level goal's priority in the same project, via a pool it doesn't otherwise interact with.** This mirrors the existing Rank/Ascension precedent (upgrade materials, alliance orbs) exactly, so it's a consistent mental model once a user already understands Potential progress for those kinds — not a new kind of surprise this change introduces.
- ~~**The XP-book id → rarity mapping (`xpBookIdRarity` in `level-xp-cost.ts`) is a best-guess** since no real Tacticus API ids are known.~~ **Resolved by Decision 6**: the guessed `bookXxx` ids were wrong (real ids use an `xp` prefix, confirmed against the app's own synced IndexedDB data) and silently zeroed the owned-books pool for every Level goal. The map now uses the verified real ids.

## Migration Plan

None needed — client-only presentation/calculation change over already-synced inventory data (the XP-book inventory chunk `getInventoryXpBooks` already reads is the same one the goal-creation cost preview already fetches). Ships and rolls back like any other frontend PR.
