## Context

See `proposal.md` for motivation. Today `GoalProgressDisplay` (`goal-visuals.tsx`) renders two separate shadcn `Progress` bars (Actual, Potential) each with an always-visible caption + full-sentence explanation, consumed by three call sites: `goals-list.tsx`'s `GoalsTable`/`GoalsMobileCards`, `goal-detail-view.tsx`, and `goal-detail-sheet.tsx`'s edit-mode header. The desktop table (`GoalsTable`) has columns Character, Type, Progress, Status, Estimate (conditional), Actions, each `TableCell` defaulting to `whitespace-nowrap` (`packages/ui/src/components/table.tsx`) with no `max-width` on the Progress cell — the root cause of the horizontal-scroll regression this change also fixes by removing the long inline text from that cell. `EstimateCell` (in `goals-list.tsx`) already renders the "📅 {{date}} · in {{days}} days" content this change's "Status · Done by" column reuses unchanged (`goal-list-estimate-display`, already shipped). The shared UI package already has `Popover` (Radix-based, portal-rendered by default, closes on outside-click/Escape natively) and `Tooltip` (with an existing touch-tap-to-open affordance for mobile, `packages/ui/src/components/tooltip.tsx`) — both reusable as-is for this change's info popover and Unlock name tooltip.

## Goals / Non-Goals

**Goals:**

- Replace `GoalProgressDisplay`'s internals (bar rendering, percent/caption, explanation disclosure) without changing its callers' data contract (`GoalProgress`, `potentialRatio`) beyond what's needed for the new remaining-text formatter.
- Rework `goals-list.tsx`'s desktop table and mobile card layout per `goal-list-layout`.
- Fix the horizontal-scroll regression as a consequence of removing the unconstrained inline explanation text (no separate patch needed once the popover lands).

**Non-Goals:**

- Not changing any progress/ratio/estimate calculation (`computeGoalProgress`, `computePotentialProgressRatio`, `calculateGoalResourceNeed`, `estimatePlan`) — this is a presentation-layer change only.
- Not touching Ability or Ascension's own progress _calculation_ — `computePotentialProgressRatio` already computes a Potential ratio for Rank, Ability, and Ascension goals alike (`plan-insights-calc.ts`'s `orbAllocations`/`allocations` branch), so the stacked bar, percent indicator, legend, and info popover are all written generically against "has a Potential ratio," not gated to Rank. The popover/mobile-expand explanation copy ("upgrade slots remaining" / project-priority reservation) is worded for Rank's remaining-count vocabulary today; an Ability or Ascension goal reaching this UI reuses the same Potential-progress explanation line without the Rank-specific remaining-count clause, since `goal-progress-display`'s explanation requirement only mandates what the Potential line states, not a per-kind remaining figure inside it.
- Not redesigning the goal-detail sheet's separate "Estimate" section, or the create-goal flow.
- Not adding a Joyride tour or new tour steps — the Goals list's tour targets are audited (see Risks) but its onboarding _flow_ doesn't change.

## Decisions

1. **Resolve the mockup's breakpoint inconsistency in favor of the app's existing 768px `useIsMobile()` switch.**
   The mockup's desktop section says "below ~900px switch to mobile cards" while its own mobile section header says "below about 768px." Resolution: the table/card switch is the app's one existing breakpoint (`goal-list-layout`'s dedicated requirement), keeping `GoalsList`'s existing `useIsMobile() ? <GoalsMobileCards> : <GoalsTable>` branch structurally unchanged.
   ~~with a separate desktop-only 1200px threshold for hiding the Remaining column~~ — **superseded, see Decision 1a below.**

1a. **(Post-implementation revision) Drop the second, 1200px Remaining-column threshold — columns are static at every desktop width.**
Decision 1 originally paired the 768px table/card switch with a second, narrower, table-internal threshold that hid the Remaining column below 1200px (Decision 2's container query implemented it). Live review feedback: hiding/restoring a column as the table resized made the page feel like it was "jumping" — the user explicitly asked for static columns instead. The Remaining column is now part of the fixed column set at every desktop width, same as Character/Goal/Progress/etc.; the only responsive behavior left is the one 768px table→card switch. The remaining-text tooltip added for the hidden-column case (Decision 2's rationale) is kept as a second, always-available path to the same figure rather than removed, since it's harmless and some callers may still prefer the tooltip over scanning the Remaining column.

2. **(Superseded — see Decision 1a) Detect the 1200px Remaining-column threshold with a container query on the table's wrapper, not `window.innerWidth`.**
   The Goals list renders inside a page layout with a fixed sidebar; the available table width is not the same as the viewport width once the sidebar is accounted for. A CSS container query (`@container` on the `Table`'s existing wrapper div, a Tailwind `@min-[1200px]:table-cell` / hide pattern) reacts to the table's actual rendered width, matching what "does the Remaining column visually fit" really depends on, and needs no JS resize listener. Alternative considered: a `useMediaQuery` hook on `window.innerWidth` — rejected because it would hide the column based on total viewport width even when the sidebar is collapsed and the table itself has plenty of room, or vice versa.
   This was implemented (Tailwind v4's native `@container` support confirmed it worked), then reverted whole by Decision 1a once live feedback called out the resulting layout shift as a usability problem, not a technical one — the container-query mechanism itself worked as designed.

3. **Build the stacked bar as a small new shared component (`StackedProgressBar`), not a variant of the existing shadcn `Progress`.**
   The existing `Progress` primitive (Radix `ProgressPrimitive`) renders one indicator layer; overlaying a second striped layer requires two absolutely-positioned fills inside one track div, which is simpler and more explicit as a small purpose-built component than forcing two nested `Progress` instances to visually overlay (`Progress` also carries its own ARIA `role="progressbar"` semantics that shouldn't duplicate). It lives in `goal-visuals.tsx` alongside `GoalProgressDisplay`, not in the shared `@workspace/ui` package — it is specific to this one dual-ratio goal-progress use case, not a general-purpose design-system primitive (mirrors how `GoalProgressDisplay` itself is already page-local, not promoted to `@workspace/ui`).

4. **Lift "which info popover is open" to one piece of state per list (`GoalsTable`/`GoalsMobileCards`), keyed by goal id, rather than local `useState` per row.**
   The spec requires only one popover open at a time across the whole list, and that opening a row's "⋯" actions menu closes any open info popover. A single `openPopoverGoalId` state (lifted to the list component, passed down as a controlled `open`/`onOpenChange` pair to each row's `GoalProgressDisplay` and cross-wired to each row's existing `GoalRowActions` `DropdownMenu` `onOpenChange`) is the minimal state shape that satisfies both constraints without a new global store. `goal-detail-view.tsx`/`goal-detail-sheet.tsx` each render exactly one `GoalProgressDisplay`, so they keep local `useState<boolean>` — the single-open-at-a-time constraint is list-scoped, not app-wide, since only one goal's popover can be visible in a single-goal detail view anyway.

5. **Reuse the shared `Popover` component for desktop; use a plain expand/collapse (no portal, no Radix primitive) for the mobile inline explanation.**
   `Popover` already gives outside-click/Escape close and portal rendering for free (Decision 3's rationale doesn't apply here — this is disclosure, not a visual overlay needing custom layering). Mobile's inline expand is deliberately not a `Collapsible`-wrapped popover or sheet: the spec calls for it to render inside the card's own layout flow (pushing content below it down), which a simple conditional render + CSS height transition achieves directly, and avoids the mockup's own noted risk ("a floating popover is awkward on touch screens").

6. **Extend `GoalProgressParams`'s farming-estimate input only for the Rank remaining-text formatter's energy segment; do not thread a new prop through every call site.**
   The "N slots · N energy" formatter needs the same per-goal `EstimateOutcome`/`energyTotal` value `EstimateCell` already receives from `estimates`. Rather than changing `computeGoalProgress`'s return shape, the remaining-text formatter is a presentation function in `goal-visuals.tsx` that takes `GoalProgress` plus the already-available `estimateEnergy(estimate)` value (existing helper in `goals-list.tsx`, promoted to a shared export) — mirroring how `GoalRemainingSummary`/`GoalEnergyRemainingSummary` already consume separately-sourced inputs today.

7. **(Post-implementation revision) Cap the percent readout at 99% until the ratio truly reaches 1, rather than rounding to the nearest whole percent.**
   Plain `Math.round(ratio * 100)` reads a ratio like 0.996 (498 of 500 shards) as "100%" while the adjacent remaining-count figure still says "2 shards" — a visible contradiction the user caught live. `displayPercent()` in `goal-progress-visuals.tsx` special-cases this: any ratio `< 1` clamps to at most 99, and only a ratio that has actually reached 1 renders "100%". No alternative was seriously considered — this is a straightforward off-by-rounding bug fix, not a design trade-off.

8. **(Post-implementation addition) Distinguish "Restricted" from "Blocked" by whether every blocker reason is `PrerequisiteNotReached`, rather than adding a third status value.**
   The user's feedback was that a prerequisite-only block (waiting on ordinary plan sequencing) reads as confusingly similar to a genuinely stuck goal (e.g. player data unavailable), and that a second, independent rendering of "Blocked" text in the estimate cell (`EstimateCell`, drawing from the same underlying blockers in the project-scoped view) duplicated the one indicator. Rather than introduce a new `GoalStatus` value or thread a new field through `goal-blocker-reasons`' existing computation, `BlockedIndicator` branches purely on the already-computed `blockers.reasons` shape at render time (`goal-blocker-reasons`' own ADDED requirement, ["A block caused solely by an unreached prerequisite presents as Restricted, not Blocked"](specs/goal-blocker-reasons/spec.md)) — no change to how or why a goal is blocked, only how that state is labeled. `EstimateCell`'s own duplicate Blocked-text branch was deleted outright rather than reconciled, since `BlockedIndicator` already covers it.

9. **(Post-implementation addition) Compute the Rank/Level reachable-ceiling as a pure derived value on `GoalProgress`, and render it as a plain absolutely-positioned tick, not a second `StackedProgressBar` layer.**
   The user asked for a marker showing what's reachable _right now_ given the character's rarity (and, for Rank, level too — "capped by both ... take it into account too"), separately from the existing actual/potential fills. `computeGoalProgress` (`goal-progress.ts`) gains a `reachableRatio: number | null` field on the `Rank` and `Level` `GoalProgress` variants: for Rank, `Math.min(rankIndex(maxRankForProgression(rarity)), rankIndex(maxRankForLevel(level)))` — reusing `maxRankForProgression` (already in `@workspace/game-domain`) and a new `maxRankForLevel` (the inverse of the existing `rankToLevel` table in `apps/web/.../goal-farming/lib/rank-additional-target.ts`, already used for prerequisite-goal suggestions) — clamped `null` once that ceiling is at or past the target; for Level, `levelCapForProgression(rarity)` the same way. `StackedProgressBar` takes this as a `ceilingRatio` prop and renders a thin `aria-hidden` tick at that position with a native `title` tooltip — presentational only, since the "Restricted" indicator (Decision 8) already carries the equivalent information for assistive tech, and a tick avoids the complexity of a third overlapping fill layer for what is a single-point marker, not a range.

## Risks / Trade-offs

- **Removing the per-row "Actual progress"/"Potential progress" caption text changes what a screen reader announces per row.** → The stacked bar keeps a single accessible `role="progressbar"` element with `aria-label`/`aria-valuetext` summarizing both ratios (e.g. "25% complete, 47% potential"), and the info popover's trigger button carries its own `aria-label` naming the goal so its content remains independently reachable — covered by `goal-progress-display`'s scenarios in the delta spec.
- **The 1200px container-query threshold is a new pattern for this codebase (a grep of existing Tailwind config/usages should confirm `@container` support before implementation; if unsupported, fall back to a `ResizeObserver`-backed hook).** → First implementation task verifies Tailwind's container-query support in this repo's config before committing to the CSS-only approach; falls back to Decision 2's rejected alternative only if genuinely unavailable.
- **Existing Joyride tour steps for the Goals page may target selectors this redesign removes (e.g. any step anchored to the old two-bar DOM structure).** → A grep of `apps/web/src/fsd/pages/goals/**/*.tutorial.tsx` for the affected `data-testid`s found no current references (see design research), but this is re-verified as a task once the new DOM/testids land, not assumed safe from this one-time grep.
- **`goal-progress-display`'s MODIFIED requirement can't be archived until `fix-goal-progress-consistency` is archived first** (see proposal.md's Impact) → sequencing is a process risk, not a code risk; tasks.md's first task is gated on confirming that change's status.
