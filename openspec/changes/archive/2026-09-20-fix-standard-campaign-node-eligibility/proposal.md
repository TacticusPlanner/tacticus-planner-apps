## Why

Today's farming engine treats every standing (standard/elite/mirror) campaign node as raid-eligible regardless of whether the player has actually reached it — `availableCampaignBattles` only gates event-campaign nodes, returning `true` unconditionally for everything else (`campaign-event-eligibility.ts:59`). A goal whose only farm location is a locked node gets recommended anyway, and because that node has no real attempt data, it renders with 0/0 attempts as "Max raids" — indistinguishable from a node the player has actually exhausted today. `2026-09-18-fix-daily-raid-location-recommendations` fixed this exact defect class for event campaigns only; this change closes the other half using the same `campaign-progress` signal the Progress page already syncs and displays, so it's grounding, not new data plumbing.

## What Changes

- **Standing campaign battles gain the same reached-node gate event campaigns already have**, and are excluded from raid calculations the same way: a battle's `battleIndex` (the zero-based index `campaign-progress` payloads are keyed against — distinct from the display-only `nodeNumber`) must be at most one past that track's `highestCompletedBattleIndex`, or it's excluded outright. A track with no `campaign-progress` entry yet only admits `battleIndex: 0`. This closes PLAN-01 (no longer recommended) and, as a direct consequence, PLAN-02 (an excluded node simply has no farmable location today — the same "not farmable, not shown" outcome an unreached event node already gets, never a misleading "Max raids" read).
- **Accepted consequence, matching existing event-campaign behavior**: when a goal needs two or more materials in the same farming stage and only one currently has a locked-only source, the existing engine drops the _whole_ stage until that material becomes reachable — not just the locked one. This is not new risk; it is the same "no farmable location" handling an event-locked material already triggers, now also reachable for standing campaigns.
- **The real-attempt/energy-tracking path is kept independent of this new eligibility filter.** `battlesById`'s eligibility-filtered map already feeds `buildBattleAttemptIndex` → `calculateRealEnergyUsedToday`/`buildAttemptsLeftByBattle`/`buildTodaysAttempts`/`locationsByBattleId` in `use-daily-raids.ts`. Extending that same filtered map to standing campaigns would risk silently dropping a real synced attempt (`live-progress.battleAttempts`, an independent signal from `campaign-progress`) whenever the two chunks are momentarily out of sync — for the much larger population of a player's not-yet-reached standing nodes, not just event nodes. This change splits the battle map: a full, unfiltered catalog map feeds the real-attempt/energy/location-label consumers (for both standing and event campaigns — an incidental correctness improvement for the existing event path too, not just standing), while only the reach-filtered map feeds the scheduling/estimate engine.
- No `locked` UI status, badge, or conditional-fallback presentation in this change — a locked standing node is excluded outright, exactly like an unreached event node already is. DAILY-06's "force-show locked anyway" toggle and any distinguishable locked-vs-exhausted display remain a possible follow-up, not built here.

## Capabilities

### Modified Capabilities

- `daily-raids-today`: "Standing campaign battles SHALL remain eligible for raid calculations" gains the same node-reached gate the event-campaign half of that requirement already has, sourced from `campaign-progress` instead of `campaign-events-progress`.

## Impact

- `apps/web/src/fsd/features/daily-raids/model/campaign-event-eligibility.ts` (`availableCampaignBattles`, `isEventNodeReached`): add a sibling reached-check for standing campaigns via `campaign-progress`, applied in the same filter pass.
- `apps/web/src/fsd/features/daily-raids/model/use-daily-raids.ts`: fetch `campaign-progress` (`getCampaignProgress`, already used by `campaigns-page.tsx`) alongside the existing `campaign-events-progress` fetch; split the battle map into a full, unfiltered one (feeding `locationsByBattleId`, `buildBattleAttemptIndex`, `calculateRealEnergyUsedToday`, `buildAttemptsLeftByBattle`, `buildTodaysAttempts`) and the eligibility-filtered one (feeding `calculateDailyRaids` only).
- No changes to `resource-card.tsx`, `daily-raids-calc.ts`'s return shape, or the shared `goal-farming` estimate engine — the engine's existing "no farmable location" handling already does everything this change needs once it receives a battle map that excludes locked standing nodes.
- No API change — `campaign-progress`'s `highestCompletedBattleIndex` already syncs per standing campaign and is already consumed by the Progress page; nothing new needs to reach the client.
