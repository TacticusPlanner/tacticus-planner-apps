## Context

See proposal.md - Why. All three issues trace back to the archived `2026-09-15-add-userjot-widget` change: `META-01`/`META-02` to `apps/web/src/fsd/app/providers/userjot-provider.tsx` and `userjot-feedback-button.tsx`; `META-03` to `apps/web/index.html`'s `uj.init()` call. That change's own design.md explicitly scoped out "UserJot Automatic Login / SSO to UserJot's own public pages... everything here happens inside the in-app widget" (still respected here — the board link needs no SSO) and separately stated the goal "drive it from a custom launcher... not the default floating button" — `META-03` is that second goal not fully realized, since `launcher: false` alone doesn't cover UserJot's other two default-on proactive surfaces.

UserJot's own documentation (fetched directly 2026-09-21):

- The widget SDK reference (`https://userjot.com/docs/widget-v3-reference`) confirms the `open()` method's `to` union includes `"notifications"` and that the `unread` event's payload is `{ count }` only — no type, id, or category.
- The `init()` options reference confirms `widget.launcher` only controls the floating button, and that `widget.whispers` (default `true`) and `widget.notifications.updates` (default `'whisper'`) are separate options controlling proactive toasts/announcements, with an explicit documented combination to disable all three.

Both are load-bearing for the decisions below.

## Goals / Non-Goals

**Goals:**

- Give testers a way to reach the public board without depending on having read a specific announcement post.
- Make "no default UserJot UI, only this app's own entry points" actually true everywhere, matching the original integration's stated intent.

**Non-Goals:**

- SSO/identified access to the public board — unaffected, still out of scope per the original design.
- Routing the click target based on unread activity. Investigated and live-verified as not reliably achievable: the `unread` event's count combines conversation replies, changelog posts, and feedback notifications with no per-type breakdown, so no single `open()` target is consistently correct — see the Decisions section's "Click always opens the widget's default view" entry. `META-02`'s underlying complaint (clicking always lands on the same default view) stands; this change narrows the fix to what the SDK actually supports (the unread indicator itself) rather than a routing behavior that would be wrong part of the time.
- Any change to UserJot Conversations exposure — stays excluded per the existing requirement.
- Adding any UserJot entry point to the unauthenticated landing page. `META-03` removes a stray default popup there; whether signed-out users should get a deliberate feedback entry point is a separate product question this change doesn't answer.

## Decisions

**Board URL is a plain constant, not an env var.** `VITE_USERJOT_PROJECT_ID` is identical across `.env.production` and `.env.staging` (same tenant everywhere), and the public board root (`https://tacticusplanner.userjot.com`) is likewise the same in every environment this app ships — there's no per-environment value to parameterize, so a constant avoids a needless env var for a value that never varies.

**A new shared `UserJotBoardLink` component, not a menu/popover.** Considered folding the board link into a dropdown behind the existing feedback button (one control, two destinations) instead of a second visible control. Rejected: a dropdown adds a click before either destination is reached, `UserJotFeedbackButton`'s single click currently going straight to the widget is worth preserving, and the header/drawer rows already comfortably fit one more small icon button/row next to the existing pattern (`ThemeSwitcher`/`LanguageSwitcher`/`UserJotFeedbackButton` are already three separate controls in the same row).

**Click always opens the widget's default view — `{ to: "notifications" }` was tried and reverted.** An earlier version of this design routed to `{ to: "notifications" }` whenever `unreadCount > 0`. Live verification (2026-09-21, signed-in account with genuine unread activity) found this actively wrong: the notifications view reported "You're all caught up" — empty — despite the unread indicator correctly showing. UserJot's own widget reference (re-fetched to confirm) states the `unread` count "includes conversation replies, changelog posts, and feedback notifications" combined into one number with no per-type breakdown available from the `unread` event or anywhere else in the SDK. A changelog post (which surfaces under the widget's "updates" view, not "notifications") is enough to raise the count, and routing unconditionally to "notifications" is then simply the wrong destination — not occasionally unreliable, but based on information the SDK doesn't give us. There is no other single target that's reliably correct either: "updates" would be equally wrong whenever the source was a reply or feedback notification instead. Reverted to the original `open()` (default view) for every click; the unread indicator itself is unaffected and remains a valid passive signal that _something_ is new, even though this integration cannot tell the user _what_ or navigate them there directly. This narrows `META-02`'s original ask — see the Risks section below.

**Set `whispers: false` and `notifications: { updates: 'none' }` in `index.html` directly, matching the existing `launcher: false`, rather than a React-level fix.** These are static `uj.init()` options in a `<script>` tag that already runs unconditionally on every page — the same reason the original design put `launcher: false` there instead of in a provider. Since `UserJotProvider` only mounts inside the authenticated `AppShell` (by design — it drives identify/theme/locale sync, all auth-relevant), it structurally cannot be the place that suppresses default UI on the unauthenticated landing page; only the global script tag runs on every page regardless of auth state.

## Risks / Trade-offs

- [Risk — realized, resolved by reverting] It was unconfirmed from static reading alone whether this project's UserJot plan/config actually populates a non-empty notifications view. Live verification (task 2.2) found it does not reliably reflect the unread indicator's source, for the structural reason in the Decisions section above (combined unread count, no per-type breakdown). → Resolution: click routing reverted to the default view unconditionally; `META-02`'s "land wherever the unread activity actually is" ask is not achievable with the current SDK and is now a documented non-goal rather than a partially-working feature. If UserJot's SDK later exposes a typed/categorized unread payload, this can be revisited. Re-verified 2026-09-21 after the revert: with the unread indicator showing, clicking the (now unconditional) `open()` button lands on the default view, which itself surfaces a "Welcome to Tacticus Planner Updates" changelog post under a "Released" section — the actual likely source of this account's unread count. This confirms the semantic-mismatch theory directly: the unread item was a changelog post, which the default view already surfaces, and which the notifications view (being a different, narrower category) correctly did not.
- [Risk — observed, out of scope] The widget's very first open in a page session reliably shows "We couldn't load this page" / "Something went sideways," regardless of target (`{ to: "notifications" }` or none) — confirmed live both before and after the routing revert. "Try again" immediately succeeds. This reproduces identically with no target, so it isn't caused by this change's routing logic; it appears to be the UserJot widget's own first-load behavior in this environment. → Mitigation: none applied — out of scope for this change (neither `META-01`/`META-02`/`META-03`'s acceptance criteria describe a loading reliability issue), and not something app-side code controls. Worth a follow-up report to UserJot if it persists in production.
- [Risk] The unread indicator clearing "once that activity has been seen" (existing requirement, unchanged by this proposal) is UserJot's own server-side behavior, not something this app computes — this change doesn't alter or verify that mechanism, only where the click navigates to. → Mitigation: none needed; this was already true before this change and isn't part of either issue's acceptance criteria being addressed here.
- [Risk] Disabling `widget.notifications.updates` (announcement auto-popups) entirely means users who never click the feedback button will never be proactively told about a changelog update, even one relevant to them. → Mitigation: accepted deliberately — the original design's whole premise was that all widget access goes through this app's own controlled entry points, not vendor-driven proactive UI; the unread indicator on the desktop button (unaffected by this change) remains the app's own passive signal that something's new.
