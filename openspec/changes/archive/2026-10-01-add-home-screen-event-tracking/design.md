## Context

V1 (`tacticusplanner`) uses Home Screen Events in three places: a manual `homeScreenEvent` dropdown in Daily Raids settings feeding `UpgradesService.sortLocationsForRaiding` and `postProcessRaidsForHse`; `HseScheduleBanner` with a hand-edited UTC schedule; and the `plan-hse` page with per-event JSON trackers.

V2 today: the events calendar (`@workspace/game-catalog`) serves `event-definitions` and `events-calendar`; `getEventsActiveAt(date)` is start-inclusive / end-exclusive UTC. The raid engine is `features/daily-raids/model/daily-raids-calc.ts` plus `features/goal-farming/lib/estimate*.ts` (`selectFarmNodes` ties on two-decimal energy per item then `expectedGold`; `spendDay` orders by longest time to finish; `allocatePlanInventory` shares inventory across goals in priority order). `features/daily-raids/model/use-eligible-campaign-battles.ts` already yields the battles a player can raid by campaign progress. Dailies tabs are driven by `app/layout/nav-items.ts` and `pages/dailies/route.tsx`; the first tab is labelled "Raids" and renders the Today page at `/dailies/raids`. The Dailies pages that depend on projects (Raids, Shops) show the Dailies-wide project selector fed by the `DailiesLayout` outlet context; Today also carries the Planning Settings trigger and dialog (`entities/planning-setting`).

### Investigation findings (settled)

**Q1 - enemy data resolves.** Every `detailedEnemyTypes[].id` in the campaign-battles data resolves to an `npcs` record. Served npcs carry `traits` (Mechanical on 101 npcs, plus a separate `Mechanic` trait on 21 that does not count), `factionId` (e.g. `Tyranids`) and `alliance` (Chaos etc.), so per-enemy matching needs no API change. Two caveats: no npc referenced by a campaign battle has a `Summon` trait (summon exclusion is a no-op in practice but is kept for correctness; the game's tracker data also excludes the `Steppable` trait, which 30 npcs have, so both are excluded); and a battle's own `enemiesAlliances` is battle-level (27 battles list two alliances), so matching uses the per-enemy npc fields, not the battle fields. Battle `type` values are `Standard`, `Mirror`, `Elite`, `EliteMirror`, `Extremis`.

**Q2 - why Machine Hunt is missing.** The calendar is hand-authored. `event-occurrences.json` has 20 records ending 2026-09-06; HSE definitions have `recurrence: None`, so nothing is projected. Nothing after early September was authored, and nothing flags a stale calendar. Date handling is a second problem: V2 occurrences start at 00:00 UTC while V1's schedule records 08:00 UTC starts, and the two disagree on the August Machine Hunt and Terminator Boost dates. Also missing: only 8 HSE definitions exist; V1 and the game have more. This is fixed by the companion API change (new definitions including `hse-purge-order`, current occurrences, a stale-calendar test).

**Raid relevance of every HSE type** (from V1's tracker data: does it award points for killing enemies in campaign modes?):

| -------------------------------------------------------- | ----------------------------------------- | ----------------- |

Events with no raid relevance still appear in the HSE tab's status line (name and remaining time) with the text that they do not earn points from campaign raids. A future event type is a one-row addition to the rule table.

## Goals / Non-Goals

**Goals:** automatic timezone-safe detection of the active HSE; an HSE tab whose main list tells the player where to spend today's remaining daily energy to earn the most event points while still feeding their goals, computed over the whole schedule; two goal-independent best-locations lists; all of it honoring the Raids Filters and the Dailies project selector and planning settings; Today and Plan unchanged; tests.

**Non-Goals:** a second filter implementation (the HSE tab reuses `add-daily-raids-filters`); the `plan-hse` points calculator and tracker pages (rewards, tiers, milestones) stay out of scope; `invertHse`; per-event settings; account-synced settings; HSE influence on Today or the Plan; a multi-day event-points plan; optimal (knapsack) packing of the energy budget.

## Decisions

1. **Single active HSE from the calendar.** `useActiveHomeScreenEvent()` in `features/daily-raids/model` queries `getEventDefinitions()` and `getEventsActiveAt(now)`, filters `type === "HomeScreenEvent"`, and exposes `{status: loading|error|ready, active, next}`. `active` is at most one event. Data model assumption: at most one HSE is active at any instant. Defensive pick if data overlaps anyway (stale or erroneous records): rank by rule-bearing first (an event with a raid-point rule beats one without), then latest `startUtc`, then lowest `definitionId`, so the result is deterministic (tested) and a non-raid-point event can never mask a rule-bearing one. `next` is the earliest upcoming HSE by start time (from `getUpcomingEvents`). Errors become a tagged result (same `loadSafely` pattern as `use-events-calendar.ts`), never a throw.
2. **Timezone: UTC only for activity.** Comparisons use `Date.parse(startUtc/endUtc)` against `Date.now()`; local time is only for display. Because the HSE tab only optimises for the event that is active now, nothing needs per-day windows.
3. **Rule table is client-side static** (`home-screen-event-rules.ts`): `Record<definitionId, rule>` for `hse-warp-surge` (npc `alliance === Chaos`), `hse-machine-hunt` (`traits` include `Mechanical`), `hse-training-rush` (all), `hse-purge-order` (npc `factionId === Tyranids`). Points: 3 per matching enemy, 5 when the battle `type` is `Elite` or `EliteMirror`; enemies with trait `Summon` or `Steppable` never count (matches the game's tracker data; V1's hardcoded raid code excluded only Summon). Per-energy score is points per raid divided by `energyCost`. Unknown HSE ids have no rule. The lookup is keyed by `definitionId` so a future API-served rules dataset can replace the table.
4. **Enemy matching data.** Resolve `detailedEnemyTypes[].id` through the `npcs` dataset once per battle set into a memo map, not per render. An unresolvable id counts as zero (never guessed). The same npc lookup (and a `battleEnemyTraits` helper beside the rules) is what the Raids Filters' Enemy traits group reuses (`add-daily-raids-filters`).
5. **The farm list is computed over the whole schedule, not from Today's picks (rework 2, supersedes every earlier "Today's raids for event points" definition, including the view-level `summarizeEventRaids` sort of Today's day result).**

   _What the user asked for._ The HSE tab's main list lists the locations the player can farm with today's remaining daily energy to earn event points, restricted to locations that actually advance an active goal. Because Today's own plan picks the energy-efficient node per material, most of its nodes earn no points and a filter or re-sort of Today's day result can never show the point-earning alternatives; so the list is chosen over the full set of needs instead.

   _Definition._ Let the scope be the active goals of the Dailies project selection (none selected = every Active goal in the global plan, in global priority order; Paused goals do not plan; a canonical goal in several projects counts once: exactly the member set Today and Plan > Schedule use). Let the **schedule need** be, per resource (upgrade or character shard), the remaining need over every stage of every goal after the Plan's priority-ordered inventory allocation (`allocatePlanInventory`), i.e. what Plan > Schedule would farm over all its days, not only day 1. A **candidate location** satisfies all of:
   1. it earns event points for the active rule (`pointsPerRaid > 0`);
   2. it is unlocked by campaign progress (the shared `use-eligible-campaign-battles` eligibility, so event-campaign nodes only while their event is active), has `energyCost > 0` and has attempts left today (the synced `attemptsLeft` when known, else the node's daily attempt cap, a cap of 0 meaning unlimited);
   3. it has a farm location with a drop rate above 0 for a resource in the schedule need that some in-scope goal needs there ("anyhow contributes to my goals"): a goal that pins `farmingLocationIds` is only served by those locations, and shard goals with campaign shards disabled contribute no location, exactly as the engine already models them;
   4. it passes the persisted Raids Filters, evaluated with the resource it drops (so the rarity criterion applies to upgrade drops).

   _Energy budget._ `budget = max(0, dailyEnergy - realEnergyUsedToday)`: the planning setting `dailyEnergy` minus the energy the player has really spent today across every campaign (the existing account-wide `calculateRealEnergyUsedToday`, attempts used times energy cost). Node attempts already used today reduce that node's attempts left (criterion 2).

   _Order._ Candidates are ordered by `ratio = pointsPerRaid / energyCost` descending; ties by `pointsPerRaid` descending, then the best (lowest) global priority among the goals the location serves, then `battleId` ascending (deterministic).

   _Fill._ Walk the ordered candidates and give each `raids = min(attempts left, floor(remaining budget / energyCost), still-useful raids)` where still-useful raids is the largest, over the needed resources the location drops, of `ceil(remaining schedule need / dropRate)`; farmed amounts are deducted from the remaining need, so two locations dropping the same resource do not both farm it past what is needed. A location with 0 raids (does not fit, need already met) is skipped, not a stop: a cheaper candidate further down may still fit. The result is the list's rows; the day total badges are the sum of row points and the sum of row energy (never above the budget).

   _Row._ location (campaign, tier, node), raids to do, expected points (`pointsPerRaid x raids`), energy (`energyCost x raids`), the goals the location serves as round unit icons (decision 13), and the drop icon of the needed resource it drops (decision 14's icon component).

   _Filter-then-pick, stated plainly._ This list behaves as if an implicit Raids Filter "earns event points" (together with the user's explicit filters) were applied before node choice: for a needed material it chooses among the point-earning nodes, instead of choosing the cheapest node and dropping it when it earns nothing (the pick-then-drop rule of Today, `add-daily-raids-filters` decision 2). So it can cost more energy per item than Today's plan: it spends energy on point-earning nodes even when a cheaper non-point node exists. The UI says so (a note under the list title). Showing the energy/efficiency cost versus Today was considered and is not built: it needs a per-resource comparison against the efficiency-optimal node for little value; it can follow later. Today, Bonus Raids, Home and Plan are untouched and never see event points.

   _Empty states._ (i) no active goals in scope; (ii) no energy budget (`budget` is 0: the setting is 0 or all of it is spent), also used when energy is left but less than every candidate costs; (iii) nothing contributes (no point-earning, unlocked location with attempts left drops a needed resource); (iv) when Raids Filters are active and would leave candidates without the filter, "no location matches your Raids Filters" with Reset. Loading and error reuse the Today `RaidState`. The status line and both top-10 lists render in every case.

   _Engine reuse decision._ New pure `planEventFarm` in `features/daily-raids/model/home-screen-event-farm.ts`, built from two pieces of the existing engine rather than a new run of its day loop: `allocatePlanInventory` (the schedule's remaining need, identical to Plan > Schedule's) and a new exported `collectFarmNodes` extracted from `pickFarmNodes` (eligible battle, `energyCost > 0`, drop rate above 0, drop rates summed per battle, optional pinned restriction), so node eligibility cannot drift from Today. The day loop (`runPlanSchedule` / `spendDay`) is NOT reused: it spends energy by goal priority and time-to-finish, picks pick-then-drop, and only emits day 1, none of which is the ratio-ordered, filter-then-pick, whole-schedule list the user asked for; forcing it (a `nodeFilter` keeping point-earning nodes plus an energy cap) would still order by priority and could not skip a node that does not fit. `calculateDailyRaids` calls `planEventFarm` when given the event inputs and returns `eventFarm`; `useDailyRaids(projectId, { homeScreenEventId })` supplies points, attempts and the budget. The earlier optional `nodeScore` tie-break (`selectFarmNodes`, `EstimatePlanParams`, `FarmNodeScore`, `eventPointsByBattleId`) and `summarizeEventRaids` are removed: nothing needs them any more and Today/Plan must not see event points.

   _Known limits (recorded, accepted)._ The fill is greedy by ratio, not an optimal packing of the budget. Flat suppliers (shop offers, Onslaught) are not modelled, so a resource a shop would cover still counts as needed. Stage order is ignored (a later stage's need counts as "anywhere in the schedule"). The list is one day, not a multi-day event plan. A node that drops several needed resources is shown with the first (by goal priority) drop icon.

6. **HSE tab content.** (a) "Farm list for event points" per decision 5; (b) "Best locations for event points (overall)": the top 10 eligible battles ranked by event points per energy (ties: higher points per raid, then lower energy cost); (c) "Best event-campaign locations": a second top 10 of the same ranking restricted to battles of the active campaign event, shown only while a campaign event is active. Eligible for (b) and (c) means unlocked by campaign progress (reusing `use-eligible-campaign-battles`), not yet raided today (no attempt used today; battles whose daily attempts are exhausted are excluded too) and passing the persisted Raids Filters (`passLocationFilter(battle, filters)` with no material, so the rarity criterion does not restrict). Each row also shows the node's reward icon (decision 14). (b) and (c) ignore goals and the energy budget but not the filter; when the filter excludes everything a list shows an empty-list message with the Reset action; they answer "where do I farm for points" for exploration.

   **Decision B, kept (recorded):** the two top-10 lists stay. They are goal- and energy-independent and include locations that drop nothing the player needs, so they are not redundant with the farm list (which is restricted to goal-contributing locations and capped by the budget); they are the browse view the farm list cannot be. They keep "not raided today" (a different rule from the farm list's "attempts left", on purpose: the lists answer "what fresh location should I try").

   **Active campaign event (verified in code).** The project's notion is `live-progress.activeCampaignEventId` (synced player data, read by `useCampaignEventStatus` and `use-eligible-campaign-battles`), not the calendar's `campaign-event` occurrence. `availableCampaignBattles` already admits a battle of an event campaign (`releaseType === "event"`, Standard and Extremis tiers) only when its campaign group equals that id and the player has reached its node. So "event-campaign battles only while a campaign event is active" needs no new rule: (b) is all eligible battles (standing campaigns plus, while an event is active, its reached nodes) and (c) is the subset whose `campaignGroupId` equals `activeCampaignEventId`; with no id synced (c) is not rendered. The farm list uses the same eligible set.

   **Assumption (reading of the user decision, to confirm in review):** "overall top 10 of all eligible locations" includes active-event battles in the ranking, so an event battle can appear in both (b) and (c); (c) is a focused view of the same ranking, not a disjoint list.

7. **Empty and degraded states** on the HSE tab: loading (skeleton); calendar read failure (inline message that event data could not be loaded, not blocking); no event active with a known upcoming event that has a rule (the status line's name, "starts in ..." countdown and start date, plus the labelled preview of decision 8); no event active with an upcoming event that has no rule (name and countdown only); no event active and none upcoming (the calendar has no scheduled event); active event without a rule (name, remaining time, text that it does not earn points from campaign raiding; sections a, b and c are not shown). Active with a rule shows the status line (name, remaining time, earns points from raiding) above the sections, with the header controls (project selector, Raids Filters trigger, Planning Settings trigger; decision 15) and the farm list empty states of decision 5. With no event to list for (nothing running or upcoming with a rule, or an event without a rule) the controls are hidden (nothing to plan or filter). The filtered-out notice of Today is not used on this tab (decision 5: filter-then-pick never reports a material as filtered out).
8. **Upcoming events: a labelled preview (rework 3, supersedes "only plans for the running event").** With no HSE running, the HSE tab computes the same farm list and top-10 lists for the **next upcoming** HSE (`next`, the earliest not-yet-started one) using that event's rule, and labels them a preview: a banner under the status line names the event, says it is not live and when it starts (relative time and local date), and says the lists use its rules and the energy left today. The status line keeps the "Next event ... starts in" countdown. The choice is one pure function, `selectHomeScreenEventListTarget({active, next})` returning `{entry, live}` or null: the running event if it has a rule (live), else the next event if it has a rule (preview), else null; a running event without a rule, an upcoming event without one (it is never skipped for a later rule-bearing event) and nothing scheduled all keep the existing no-rule / nothing-scheduled states with no lists or controls. The project selector, Raids Filters and Planning Settings triggers show in preview mode too. Energy budget semantics are unchanged (planning-settings daily energy minus energy really spent today); in preview the banner says this is today's energy, since the event may start after the daily reset. The active-campaign-event top 10 follows the same rule (shown whenever `activeCampaignEventId` is set). A preview never changes Today, Bonus, Home or the Plan, which never react to events at all.
9. **Navigation.** Add an `/dailies/hse` child in `nav-items.ts` positioned after Raids, with label key `dailies:tabs.hse` ("HSE" in en; localized abbreviation in de, es, fr) and a description key spelling the full name. Add the route in `pages/dailies/route.tsx`. The existing label for the Today page remains "Raids". The tab is always visible, including when no event is active.
10. **UI.** Page `pages/dailies/ui/hse-page.tsx` composes feature components from `features/daily-raids/ui` (status line, farm list section, top-locations list), reusing the `homeScreen` event icon/colour from the home calendar through a shared export, and the Raids Filters trigger/dialog exported by `features/daily-raids`. Desktop: the farm list beside a column holding the overall top 10 and, when a campaign event is active, the event-campaign top 10 below it; mobile: stacked in the order farm list, overall top 10, event-campaign top 10. `data-testid`s on each section. Row layout follows the existing event location row (icon, campaign and node, trailing badges: goal icons, raids, points, energy, drop icon).

The translation-coverage tests cover all four locales.

15. **Stock chip on farm rows (rework 3).** Beside each row's drop icon the row shows "X/Y" (small chip, tabular numerals, no wrapping inside the chip; the row's trailing badges already wrap on a 420px width): X is what the player holds of the dropped item and Y its total target over the goals in scope, i.e. the same project/goal scope as the list. ## Risks / Trade-offs

- Rules are a hand-maintained table and go stale when the game adds a raid-relevant HSE; unknown ids simply have no rule, and the tab says the event does not earn raid points. Mitigation: the API stale-calendar test and the explicit table above.
- Existing calendar data overlaps (three HSEs on 2026-08-09). Settled: that is stale data, not a game rule. The defensive pick (rule-bearing first, then latest start, then id) stays in case data overlaps anyway.
- Calendar gaps (an HSE not yet authored) look like "no event"; the empty state words it as "no event scheduled", not "no event running in game".
- The farm list can ask for more energy per item than Today's plan (it prefers point-earning nodes). Accepted by decision and stated in the UI; Today stays the efficiency-optimal plan.
- Greedy fill and the ignored shop/Onslaught suppliers (decision 5 limits) can leave budget unused or list a resource a shop would cover; acceptable for a "where to spend today's energy for points" list.
- Coupling to `add-daily-raids-filters`: this change cannot be applied first because it imports the filter plumbing; without it the HSE tab would ship unfiltered, which contradicts the spec.
- `hide-premature-dailies-pages` and this change both touch Dailies navigation; apply that one first. At sync, update the main spec's "3 primary tabs" wording to four.

## Coordination with `add-daily-raids-filters`

Order: **`add-daily-raids-filters` is applied first** (decided); this change depends on it. The filters change defines `FarmNodeFilter`, `buildFarmNodeFilter`, `passLocationFilter`, `useRaidsFilters`, the trigger/dialog and (reopened) the Enemy traits group. This change consumes the predicate as one candidate rule of the farm list in filter-then-pick mode (the filters change records this as the one place the pick-then-drop rule does not apply) and mounts the shared trigger on the HSE page. There is no longer a shared `selectFarmNodes`/`EstimatePlanParams` addition between the two changes. The two API changes remain independent (both move the catalog manifest snapshot: apply in sequence, promote after each).

Settled: the first Dailies tab stays labelled "Raids" and "HSE" follows it; the 2026-08-09 overlap is stale data (see Risks); the top-10 reading in decision 6 is recorded as an assumption.
