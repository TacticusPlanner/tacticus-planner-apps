## Context

`add-home-screen-event-tracking` (applied in the working tree, not yet archived) adds the `/dailies/hse` tab (`dailies:tabs.hse` already exists in `nav-items.ts`), `selectActiveHomeScreenEvent` (pure; returns `{active, next}`) and `useActiveHomeScreenEvent` (a Dexie `useLiveQuery` over the local catalog calendar, one-minute tick, tagged `loading | error | ready`). Navigation is rendered in several places that each map `navItems`: `desktop-layout.tsx` (side menu), `desktop-section-navigation.tsx` (section menu children, via `nav-child-row.tsx`), `section-tabs.tsx` (header tab row), `mobile-layout.tsx` with `mobile-nav-link.tsx` (bottom bar) and `mobile-drawer-sub-item.tsx` (drawer), and `desktop-navigation-dialog.tsx`. The Home page is `pages/home/ui/home-page.tsx`: Token Availability (full width), then a `md:grid-cols-2` row (Projects, Raids), then the events calendar. `RaidsWidget` is the pattern for an activatable card (`role="button"`, Enter/Space, `navigate`).

## Goals / Non-Goals

**Goals:** a consistent, accessible live signal in every nav renderer; a Home card previewing the live and next HSE; one selection logic for tab, nav and card.

**Non-Goals:** changes to HSE tab content or raid rules; other event types in the card (extensible later, HSE only now); calendar data (API) changes; notifications.

## Decisions

1. **Order and dependency (decided).** This change applies after `add-home-screen-event-tracking` and its sync/archive. Main `dailies-navigation` still says three tabs until that sync, so this change uses ADDED requirements only (no MODIFIED against text that is about to change). Same for `home-token-availability`, whose "full width" sentence is superseded by an ADDED requirement rather than rewritten; `home-events-widget` is a new capability. Sync order: HSE change first, then this one.
2. **Indicator trigger (decided).** Any active HSE lights the indicator, not just rule-bearing ones, because the question answered is "is an event live", not "can I raid for points". Rule-bearing status stays an HSE-tab concern.
3. **One flag, one component.** `NavItem` and `NavSubItem` gain an optional `liveIndicator?: "hse"` (a flag naming the signal, so other signals can be added; absent means none). The HSE child sets it, and the Dailies parent sets it too (parent shows it when the HSE signal is live, visible when collapsed). A shared `NavLiveDot` in `app/layout` renders the dot plus visually hidden localized text (`nav.eventLive`), takes the flag, and renders nothing when the signal is off. Each of the four renderers (and the bottom-bar link) calls `<NavLiveDot item={...} />` next to the label. No renderer contains its own logic.
4. **Shell data and layering.** The `app` layer may import `features` (FSD direction is app to features), so the shell reads `useActiveHomeScreenEvent` through the `features/daily-raids` public API. To stay cheap, the hook runs exactly once: an `HseLiveProvider` (small context in `app/layout`) mounted in the authenticated shell calls it and exposes a boolean `isLive` (`status === "ready" && active !== null`); `NavLiveDot` reads the context. Mounting each dot with its own hook would multiply live queries and 1-minute timers across six or more instances. The provider is skipped for anonymous visitors (Dailies and HSE are not anonymous-allowed), so the landing page does no calendar read. The query is a local IndexedDB read, so no network cost. The import goes through the barrel, and the task list checks `lint:fsd` and that the shell does not pull feature UI into an eagerly loaded chunk beyond what the barrel already costs; if it does, export the hook from a narrower public path instead of importing a UI barrel.
5. **Desktop and mobile split.** The same flag and component serve both; what differs is placement. Desktop: dot beside the label in the side menu (also in the collapsed icon rail, as a corner dot on the icon), in section menu children and in the navigation dialog. Mobile: dot beside the tab label in `section-tabs`, a corner dot on the Dailies bottom-bar icon, and beside the HSE entry (and the Dailies section) in the drawer. Joyride selectors are unaffected.
6. **Accessibility.** The dot is `aria-hidden`; a sibling `sr-only` span carries the localized "event live" so it is announced with the link name, not as colour. A pulse uses `motion-safe:animate-pulse` (disabled under `prefers-reduced-motion`); the static dot remains.
7. **Data shape (decided).** Extend the selector rather than duplicate it: `selectActiveHomeScreenEvent` keeps `{active, next}` and adds `upcoming: TEntry[]`, ascending by start, excluding the active one; a small pure helper `selectHomeScreenEventPreview(selection, limit = 2)` returns `[active, ...upcoming].slice(0, limit)` with a `live` marker. `useActiveHomeScreenEvent` passes the new list through, and `next` stays `upcoming[0]` for existing consumers. The query horizon (400 days) already covers it.
8. **Home card.** `pages/home/ui/events-widget/home-events-widget.tsx` (named to avoid the existing `events-calendar` folder), titled by i18n key `home.events.title` = "Home Screen Events". It is distinct from the calendar card ("Events calendar"). Rows use the shared HSE icon/colour, the event name from the `events` namespace, and: live row = visible LIVE badge plus "ends in {countdown}"; upcoming row = local start (`Intl.DateTimeFormat` with the device timezone, display only; activity stays UTC) plus "starts in {countdown}". Countdowns reuse the existing `formatExactCountdown` (h:mm:ss) from token-availability if it is acceptable for multi-day gaps (hours are unbounded, so `49:00:00`); a day-level phrase is better for upcoming events, so use a coarse relative phrase for "starts in" if the existing `Intl.RelativeTimeFormat` helper used by the calendar fits, otherwise the exact format. Decided at implementation by reading the calendar's helpers; either must be localized and ticking at most once per minute.

   **Outcome (apply):** neither existing helper fits. `formatExactCountdown` is h:mm:ss (`49:00:00` for two days) and `formatRelativeTime` reads the wall clock itself, so it cannot be driven by the hook's `nowMs` and is not pure. The card uses its own small pure formatter, `formatEventCountdown(targetMs, nowMs, locale)` in `pages/home/ui/events-widget`: from one day out it gives whole days rounded to the nearest ("5 days"; this matches the HSE tab's "ends in" wording), under a day it gives hours and minutes ("3 hr 20 min", or one unit alone), never below "1 min". Units are localized through `Intl.NumberFormat` unit style, and the i18n strings wrap the span ("Starts in {{when}}" / "Ends in {{when}}"). The token card and its formatter are untouched. The card follows the Raids widget activation pattern with `data-testid="home-events-widget"`. Page-to-page imports are avoided: the countdown helper is imported only if it is exported by a shared slice; otherwise it moves to `shared/lib` or the widget uses its own small formatter (tests cover regression for the token card if moved).

9. **Layout.** `home-page.tsx` becomes: a `grid grid-cols-1 gap-4 md:grid-cols-2` row holding TokenAvailability and the new widget, then the Projects/Raids row, then the calendar. No new breakpoint. Token entries already `flex-wrap`, so they reflow in the narrower card; verified manually and by a render test that all entries remain.
10. **Tutorial.** `home-page.tutorial.tsx` adds a step for `[data-testid="home-events-widget"]` after Token Availability, desktop and mobile share the same steps (single column on mobile still resolves the same selector); i18n `tour.home.steps.hseWidget.*` in all four locales; update `home-page.tutorial.test.tsx` and the calendar-position expectations if any.
11. **i18n.** `common` (nav and home strings: `nav.eventLive`, `home.events.*` title, live badge, ends in, starts in, empty, error, loading) and `events` (tour step, matching home's existing tour keys) in en, de, es, fr with real translations; translation-coverage tests must pass.
12. **Calendar gap.** After 2026-10-10T08:00Z no HSE is authored in the API calendar (the second Against the Tide run is unauthored). Both the nav indicator (off) and the card (empty body) behave correctly with that data; filling the gap is an API data task outside this change.

## Risks / Trade-offs

- A lit indicator for a non-raid event (for example Faction Boost) may suggest a raid benefit that is not there; mitigated by the accessible wording "event live", not "raid bonus", and the HSE tab explaining the event.
- One shell-level live query for the whole session: cheap (local, 1-minute tick) but permanent; acceptable, and the provider is skipped when signed out.
- Narrower Token Availability card at `md` (768px) could crowd five token entries; they wrap, and manual desktop verification checks 768px.
- Behavior depends on the HSE change being synced; applying earlier would reference a tab and hook that main specs do not yet describe.

## Open Questions

None blocking. Where the exact countdown helper lands (design decision 8) is settled when reading the calendar helpers at apply time.
