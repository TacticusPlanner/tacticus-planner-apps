## Context

See proposal.md for motivation; specs define the behavior. Current state that shapes the design:

- `packages/game-catalog` already syncs `shops` and exposes the shop resolver (`resolveShopSlotsForDay`, `resolveEventLockId`, `computeShopLockContext`, `plTier`) — the event lock vocabulary (`lock_mythic_shop_tier_*`, `lock_below_max_legendary_*`, …) was ported from V1 with it.
- `features/shops/rewards` resolves reward/currency ids to labels and icons; `features/shops/recommendations` aggregates shard / mythic-shard / uncraftable Mythic needs per scope (`aggregateShopNeeds`, not yet exported); `features/goal-planning` computes `PlanMissingResources` (badges, orbs, forge badges, components, XP, gold).
- Dailies is a protected section with lazy page routes; HSE/HRE/Quest are its event tabs.
- Per-profile plan precedent: `entities/legendary-event/api/legendary-event-plan.{api,queries}.ts` over the generated client, with revision-guarded writes.
- The API dates event shops from the events calendar's `ShopEvent` occurrences and adds a new calendar definition `armageddon-shop` with June and October 2026 weeks. Home's events calendar names definitions from `public/locales/*/events.json` and links some to the wiki (`pages/home/model/event-wiki-links.ts`), so the new id needs a name there.
- Companion API change `add-event-shops` serves `GET /api/v1/game-catalog/event-shops` and `GET /event-shop-plans`, `GET|PUT|DELETE /event-shop-plans/{eventId}` (`EventShopPlanResponse { eventId, revision, catalogVersion, entries[] }`, entry `{ week, day, slotIndex, rewardType, quantity, purchasedQuantity, draftAlliance? }`, 409 `eventShopPlanStale`). The staging `ImportFromProductionResponse` also gains an additive `eventShopPlans` count; the apps need no change for it.
- The visual design is settled in the Claude Design canvas "Event shop page: directions" (https://claude.ai/artifact/7DFC1W6RfWboNfC7T2cYou), FINAL rows: `Final-Desktop`, `Final-Dialogs`, `Tablet-Closed`, `Tablet-Drawer`, `Final-Phone-Shop`, `Final-Phone-Plan`, `Final-Phone-Sheet`, `Final-Phone-Rewards`, `German`. Earlier rows are history. The canvas's own palette maps onto the V2 theme tokens; its layout, hierarchy and copy are the reference.
- Game names: `upgrades`, `equipmentItems`, `characters`, `mows` locales already name every October 2026 reward; the seasonal mission task texts (`Quests/<task>_description`, e.g. `TraverseHexes`), the chain names (`Quests/October2026FreeMissionChain` = "TRENCH FIGHTERS – {[CHAIN_POSITION]}/{[CHAIN_LENGTH]}") and game-mode names (`Quests/Quest_GameMode_<mode>`) are in the datamine's language files but not yet generated into locales (`scripts/generate-game-names-i18n.mjs` only emits mythic quest tasks). The event currency and event-points names are filled at game runtime and are not in the datamine.
- The planner already calls the shop tier "Your tier: Low / Mid / High" on the HSE page (`dailies.hse.details.tiers` / `tierRules`), with the same rule as `plTier` (`PL_MEDIUM` = 20).

## Goals / Non-Goals

**Goals:**

- One canonical per-entry classification feeding the shopping list, its totals and coverage supply.
- Reuse existing shop resolution, reward display and need aggregation through public slice APIs.

**Non-Goals:**

- A public Library browsing page for event shops, Today/Home integration (e.g. "a planned event item is on sale today"), calendar links, alerts (feedback LIB-10), currency budget forecasting, V1 cart import — follow-ups.
- Battle-pass missions and live event progress (no data source).

## Decisions

### D1. FSD ownership

- `packages/game-catalog`: dataset key, schema, store, `getEventShops`/`getEventShop` queries, and pure helpers `eventDayIndex`, `eventStatus`, `eventDay(event, index) → { week, date, dow }`, `defaultEventDay`, `resolveEventDaySlots`. Pure and time-injected (`now` parameter) for tests.
- `entities/event-shop`: generated-client wrappers `event-shop-plan.api.ts`, TanStack queries/mutation `event-shop-plan.queries.ts`, entry types. Public API: `useEventShopPlan(eventId)`, `useSaveEventShopPlan(eventId)`, types.
- `features/shops/event-planner`: model only — `cart.ts` (add/replace/set quantity/mark all bought/bought fewer/remove, all of today bought, needs-review Bought / Bought some / Missed, clear week, undo bought ahead, draft alliance, drop-unresolvable), `classify.ts` (per-entry `{ bought, toBuy, missed, state, boughtAhead }`), `day-state.ts` (per-day planned state for the calendar and chips, derived from `classify`), `slot-labels.ts` (tier / unit-progress subtitle per resolved slot), `shopping-list.ts` (groups and totals derived from `classify`), `coverage.ts` (rows), `use-event-shop-cart.ts` (optimistic state + debounced save + 409 handling), `unit-shard-search.ts`. Public API via `index.ts`.
- Cross-feature inputs through `@x`: `features/shops/recommendations/@x/shops/event-planner/index.ts` (shop needs), `features/goal-planning/@x/shops/event-planner/index.ts` (missing resources). Reward display helpers come from `features/shops/rewards`' public API.
- The shop slices form one slice group, `features/shops/` (`recommendations`, `rewards`, `event-planner`): the new slice took the features layer past Steiger's 20-slice limit. A cross-import for a grouped consumer is named by its group path (`@x/shops/<slice>/index.ts`).
- `pages/dailies/ui/event-shop/`: page, the three layout forms, header, week calendar and day chips, slot cards and tiles, slot sheet, shopping list (side column, drawer, Plan tab share one component), coverage, rewards (milestones, chests, missions), search, dialogs (Clear week, alliance, replace option, bought fewer), `event-shop-page.tutorial.tsx`. Route added to `pages/dailies/route.tsx`; nav child in `app/layout/nav-items.ts`.

### D2. One classification, everything derived

`classifyEntry(entry, todayIndex) → { boughtPacks, toBuyPacks, missedPacks, state: "done" | "needsReview" | "upcoming", boughtAhead }`. Shopping-list groups, the three totals and cart total, the calendar's and chips' per-day state, the Needs review count (Plan badge, bottom bar, drawer button) and coverage `planned` all reduce over the same `ClassifiedEntry[]`. Needs review "Missed" and Clear week share one operation, `dropUnbought(entry)` (`quantity := purchasedQuantity`, remove at 0), so no new saved state is needed: the API's entry shape is unchanged. The cost and pack size come from resolving the entry against the catalog once (`resolveEntry`), also used to detect unresolvable entries. _Alternative:_ V1's separate `effectiveCartTotalsByType` and list totals — rejected; that duplication is what produced #508's coverage bug.

### D3. State ownership

Event id is the path param; `day` and `tab` are search params owned by the page component (sibling tabs share them; switching tab keeps `day`). `tab` accepts `shop|milestones|missions|plan|rewards` and is normalized per form (spec: layouts). The default day is computed from the catalog helper, never stored. The Upcoming/All toggle and the tablet drawer's open state are local component state (not persisted). The header's "Synced N ago" reads the player-data sync timestamp the app already holds; the reset time is `00:00 UTC` formatted in the browser's time zone. Cart state is server state in TanStack Query; `use-event-shop-cart` keeps an optimistic copy, debounces 400 ms, keeps one PUT in flight and re-queues the latest set; on 409 it replaces the cache with `current` from the error and drops the pending edit.

### D4. Three forms: desktop, tablet, phone

Breakpoints: phone < 768 (`useIsMobile()`), tablet 768–1023, desktop ≥ 1024 (a page-local `matchMedia('(min-width: 1024px)')` hook; this page is the only consumer of a tablet breakpoint).

- Desktop: tabs Shop · Milestones · Missions on the left with the week calendar inside Shop; sticky side column (shopping list + Coverage) on the right.
- Tablet: same tabs and calendar at full width; the side column's content moves into a right `Sheet` (drawer) opened by a sticky bottom "Shopping list" button carrying Still to buy and the review count. Why not the side column: at 768–1023 px it leaves the card grid one column wide (the canvas's tablet boards).
- Phone: tabs Shop · Plan · Rewards; day chips; three-column tiles with a corner tick (a separate 48 px hit area so the tile tap still opens the sheet); slot `Drawer` (bottom sheet) for cart controls; sticky "Still to buy" bar on Shop.
  The shopping list and Coverage are one component tree rendered into the side column, the drawer or the Plan tab. Tour: three step arrays with distinct `data-testid` targets (`event-shop-side-column`, `event-shop-list-button`, `event-shop-tab-plan`; `event-shop-week-calendar`, `event-shop-day-chips`).

### D5. Coverage inputs and units

Needs scope = all Active goals, or one project via the same project filter control the Today shop recommendations use. Shards / mythic shards / Mythic materials come from `aggregateShopNeeds` (`required − acquired`); badges, orbs, forge badges, components, XP and gold from `PlanMissingResources`. Reward-type mapping: `abilityToken<R>_<Alliance>`, `heroAscensionOrb<R>_<Alliance>`, `itemAscensionResource_<R>`, `gold`, `xpRare|xpLegendary|xpMythic` (converted to raw XP with the catalog XP-book values, displayed as books of the selected rarity), `shards_<id>`, `mythicShards_<id>`, Mythic upgrade ids; `draft_abilityTokens<R>`, `draft_ascensionOrbs<R>` and `draft_machinesOfWarTokens` resolve by the entry's alliance (MoW tokens → that alliance's components). Unmapped reward types get no coverage row. All costs are in the event currency, and a row prices its whole still-needed amount even when it is short (the planner doesn't know the player's balance, so a capped price would understate the gap); "N short" and "only M left to buy" carry the cap. No row is highlighted.

### D5a. Game text for missions and names

Extend `scripts/generate-game-names-i18n.mjs` with a new `eventMissions` namespace in all four locales: seasonal task templates (`Quests/<task>_description` for every task of the `seasonal_daily` / `seasonal_seasonal` / `seasonal_seasonal_premium` quest groups), chain names (`Quests/<Month><Year>{Free,Premium}MissionChain`) and game-mode names (`Quests/Quest_GameMode_<mode>`). The page fills `{[TARGET_AMOUNT]}`, `{[GAME_MODE]}`, `{[CHAIN_POSITION]}` / `{[CHAIN_LENGTH]}` and strips the game's `<style>` tags. _Alternative:_ hand-written English mission texts — rejected; the game ships all four languages. The event currency and event points are named by the planner's own labels ("Event currency", "Event points") because the game fills them at runtime. Reward names reuse the planner's existing labels (`shops.reward.*`: "Gold", "XP book (Mythic)", "Mythic Imperial ascension orb") and generated names (upgrades, equipment items, units); token rewards use the game terms ("Requisition Order", "Blessed Requisition Order", "Salvage").

## Risks / Trade-offs

- [Coverage overstates the gap between buying and syncing] → stated as an assumption in the spec; the row tooltip says "Sync after buying to update".
- [Whole-set PUT on every edit] → debounced, at most ~450 entries; fine at current sizes. Revisit if plans grow.
- [Ended events dominate the picker over time] → newest first; old events remain viewable (a plan may exist).
- [V2 derives no need for some sold resources (e.g. stamina, gems, summoning tokens)] → those rewards show in the shop but get no coverage row, same as V1.

## Migration Plan

Additive: new store (IndexedDB version bump with full `stores()` block), new route and nav item. Ships after the API half is deployed; if the API lacks `event-shops`, the page shows the absent-dataset empty state.
