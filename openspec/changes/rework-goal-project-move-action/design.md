## Context

See proposal.md - Why. The current implementation lives in `apps/web/src/fsd/pages/goals/model/projects/use-remove-goal-from-project.ts` (the `remove()`/`planFor()` hook) and `project-removal.ts` (`planProjectRemoval`, the pure relocate/conflict/unavailable decision), consumed only from `goal-row-actions.tsx`'s "⋯" menu. `planProjectRemoval` always targets the Default project (`defaultProject` param) when relocating; there is no notion of a user-chosen destination today. Project creation goes through `useProjectActions.create(name, description, color)` (`apps/web/src/fsd/features/project-management/model/use-project-actions.ts`), consumed by `ManageProjectsSheet`'s `ProjectForm`.

## Goals / Non-Goals

- Goal: the goal row's own project-removal action gets a user-chosen destination (existing project or a newly created one) exactly when relocation is needed (last membership); a goal that already has another membership keeps today's plain, destination-free removal.
- Goal: desktop inlines Move-or-Remove and Delete as icon buttons; mobile is unchanged (still the "⋯" menu).
- Non-goal: the goal's edit-form membership editor (project chips) keeps its existing silent-relocate-to-Default / blocked-with-explanation behavior. The screenshot this change is built from is the row's "⋯" menu, not the edit form, and reworking the editor's chip-removal flow the same way is a larger, separate UX decision this change does not make.
- Non-goal: no change to how a goal is added to additional projects (bulk assembly, the chip picker) — only how it leaves its last one.

## Decisions

- **Parameterize `planProjectRemoval`'s destination instead of hardcoding Default.** Add a `destinationProjectId` (or the full destination `ProjectSummary`) parameter; the occupied-slot conflict check and the "goal occupies no slot" bypass work identically against any destination. This only affects the goal row's own action — `planProjectRemoval` has exactly one caller today (`use-remove-goal-from-project.ts`). The goal's edit-form membership editor (`goal-projects-field.tsx`) does **not** call `planProjectRemoval` at all; it has its own, independent `remove()` (relocating to Default with no conflict check). That's an existing, separate implementation of a similar policy, not a shared one, and this change does not touch it — see Non-Goals. Alternative considered: unify the two into one shared function — rejected as out of scope; the editor's `remove()` isn't part of what this change is asked to rework, and giving it the same conflict-check/parameterized-destination treatment is a separate change.
- **The picker is a `Dialog`, controlled by local state, mirroring `DeleteGoalDialog`'s existing pattern in this same file** — not a `Popover` anchored on the icon button, and not a `DropdownMenuSub`. `DeleteGoalDialog` already proves this pattern works identically from both triggers: a desktop icon button's `onClick` and a mobile `DropdownMenuItem`'s `onSelect` (`event.preventDefault()` there, same as Delete does today) both just set `pickerOpen(true)`; the `Dialog` itself renders outside the `DropdownMenu` tree, so it isn't affected by the menu closing/unmounting. A `Popover` was considered and rejected: it needs a visible anchor element to position against, which doesn't exist on mobile (Move-to-project is a `DropdownMenuItem` there, not an icon button), and opening one synchronously from a closing `DropdownMenuItem`'s `onSelect` is a known Radix overlay-nesting hazard. The dialog lists the account's other non-archived projects (Current plan included — nothing about being Current plan makes a project an invalid destination) as clickable rows, plus a trailing "Create new project…" row. Selecting a project moves the goal there immediately (same conflict handling as today's relocate). `AddGoalsToProjectSheet`'s pattern was also considered and rejected as heavier than this needs — that Sheet solves a many-goals/many-projects assembly problem, this is a single goal choosing a single destination.
- **When there is no other existing project, skip the dialog's picker list and open `ManageProjectsSheet` in create mode directly** on the same trigger (icon click on desktop, menu item select on mobile) — satisfies "single action, no dead-end tooltip" without a picker that would render with nothing in it.
- **Reuse `ManageProjectsSheet`'s create form for "Create new project…"** rather than building a second, cut-down create dialog — keeps name/description/color creation consistent everywhere a project gets created. This needs the new project's id back once saved. `useProjectActions.create` is built on the shared `run(action)` helper, which resolves to a plain `boolean` regardless of what `action()` returns — but `setGoalsStatus` in the same file already works around exactly this by capturing its result in a local variable the `run()` callback closes over (see its `transitioned` variable). Apply the same pattern to `create`: capture the resolved `ProjectSummary` from `createProject(...)` in a local variable inside the `run()` callback, and return that captured value (or `null`) instead of the raw `boolean` — no change to `run()` itself. Add an optional `onCreated?: (project: ProjectSummary) => void` prop to `ManageProjectsSheet`, called with that value instead of the default close-only `onSaved` behavior when supplied. Alternative considered: look up the new project afterward by name in the refetched project list — rejected as fragile (duplicate names, race with the list query).
- **Icons**: `FolderInput` (lucide-react) for the inline Move-or-Remove action (used for both the plain-removal and the move-with-picker case — same slot, same icon, different behavior depending on membership count), `Trash2` for Delete. Both sit after the existing Pause/Resume icon, before the conditional "⋯" trigger.
- **"⋯" trigger renders only when it has content.** `GoalRowActions` already knows whether Archive/Unarchive applies (`reached`, `row.status`); compute that once and skip rendering `DropdownMenu` entirely when neither applies, on desktop. Mobile keeps rendering the full dropdown (Move-or-Remove, Delete, Archive/Unarchive) unconditionally, matching today.

## Risks / Trade-offs

- [Changing `useProjectActions.create`'s return type from `boolean` to `ProjectSummary | null` touches a function other project-creation call sites use] → Checked: `ManageProjectsSheet`'s `ProjectForm` is its only consumer today; the change is truthy-compatible (`result.then((ok) => ok && onSaved())` keeps working, just with `ok` now holding the project or `null`), so that call site needs no logic change beyond its type narrowing.
- [A goal with exactly one membership, viewed on a route where that membership is a _different_ project than the one this row happens to render in — not possible today: the row action is only ever offered within the project it's rendered under, per `goal-project-membership`'s "Removal is absent without project scope"] → No new risk, existing invariant already rules this out.
